### 1.3 上游协议要点(v2.2,与本项目设计对照)

- 端口 53317(UDP 组播 + HTTP);组播组 `224.0.0.167`(上游特意选择:部分 Android 设备限制其他组播段)
- 指纹 = HTTPS 证书 SHA-256(与 DDD 4.3 一致)
- prepare-upload 已含 PIN 支持(401/403/409/429 语义与我们设计同构);upload 带 sessionId/fileId/token、SHA-256 校验 422(与 DDD 4.5.4 一致)
- **download API**:纯 HTTP 浏览器接收端——上游已实现 PRD 开放问题 O2(Web 接收端),免费获得
- 发现:UDP 组播通告 + HTTP 全网段探测兜底(与 DDD 双通道思路一致,细节不同:上游用组播而非广播)

## 2. Apache-2.0 义务清单与本项目操作

Apache-2.0 为宽松许可:**允许自由使用、修改、再分发、商用;修改部分可以自选许可(含闭源);不强制开源衍生作品。** 再分发时的义务与我们的对应操作:

| # | 义务(Apache-2.0 条款) | 本项目操作 |
|---|---|---|
| 1 | 向接收者提供 Apache-2.0 许可证文本 | 保留仓库 LICENSE 文件原样,随源码与发布附件分发 |
| 2 | 保留版权/专利/商标/归属声明 | 不删除、不篡改源码文件头的既有声明 |
| 3 | 显著标注被修改的文件 | 修改处统一加注释头 `// AnyShare modification (YYYY-MM-DD): …`;仓库根维护 `MODIFICATIONS.md` 索引 |
| 4 | NOTICE 文件内容复现(如有) | 上游无 NOTICE 文件 → 无此义务 |
| 5 | (良好实践,非强制)声明衍生来源 | README 首屏注明 "Based on [LocalSend](https://github.com/localsend/localsend) (Apache-2.0), Copyright 2022-2026 Tien Do Nam" |
| 6 | (第 6 条)商标不授权 | **必须改**:名称 LocalSend→AnyShare、Logo/图标/配色全部替换、bundle id(`com.localsend.*`)改为自有前缀,不得使用上游应用图标与名称做任何分发 |

**我们新增文件的许可选择**:新增文件(信任模型、鸿蒙端、分享集成等)默认采用与上游相同的 Apache-2.0(简化合规、便于双向贡献);如未来需商业化细分再评估。

**分发合规**:GitHub Releases 分发二进制 = "再分发",上述义务同样适用于二进制(在 Release 说明中附 LICENSE 与源码仓库链接)。

## 4. 技术路线变更(取代自研路线的部分)

| 原自研设计 | fork 后状态 |
|---|---|
| Flutter 单代码库(D1,已确认) | ✅ 不变——上游正是 Flutter,与 D1 天然一致 |
| 自研发现/传输协议(D2) | ⛔ 取代——直接采用 **LocalSend protocol v2.2**;DDD 第 4 章作为内部设计参考保留,实现以上游协议为准 |
| 端口 53318 避让(D8) | **修订:默认 53317**(与上游一致,优先保证与 LocalSend 生态互通);被占用时顺延并在发现报文中广播实际端口(报文含 port 字段,双装共存无冲突) |
| 与 LocalSend 互通(O3 待决) | ✅ **自动解决**——实现同一协议即天然互通,无需双协议栈 |
| 浏览器接收端(O2 待决,P2) | ✅ **免费获得**——上游 download API 已实现 |
| SAS 配对(D3) | ✅ 保留为 **AnyShare 扩展**:AnyShare↔AnyShare 走 SAS;与 LocalSend 客户端交互自动退回其 PIN 模式 |
| 信任模型(裁决-3/4:临时/一般/完全/同归属者+三模式限制) | ✅ 保留为核心差异化扩展,以**向后兼容方式**扩展协议(§5) |
| 六端 UI 自研 | ⛔ 大幅缩减——沿用上游 UI 骨架,改造品牌与交互细节,新增设备详情页 |
| iOS(裁决-6 排除) | **代码免费保留**(上游含 iOS),仅分发需 Apple 账号(暂无)——维持"不投入适配精力、不分发",未来补账号即得 |
| 断点续传 `.part` sha256 命名(D5) | 按上游既有机制;上游 upload 的 offset/token 语义即续传基础,细节以实现为准 |
| Android 直读分享 URI(D6) | 上游 Android 已是 share target;D6 决策继续适用于我们的增强 |

**核心增量(我们的开发重点,自上而下递减)**:
1. **鸿蒙 NEXT 移植**(上游完全没有,最大差异化)
2. **微信/QQ/文件管理器深度分享集成 + 桌面右键/拖拽增强**(上游入口浅)
3. **信任分级与限制管控**(上游仅 PIN,无归属者/限额概念)
4. 中文体验与国产 ROM 适配打磨

## 5. 协议扩展原则(信任模型如何进入 v2.2)

1. **只增不改**:新增端点(如 `/api/anyshare/v1/trust/*`)与新增字段;不修改既有端点语义。
2. **未知字段双方忽略**:AnyShare↔LocalSend 互通时,对端无视我们的扩展字段,基础互传不受影响。
3. **能力协商**:`/info` 的 AnyShare 扩展字段(如 `anyshare: {"proto":1,"sas":true}`)声明扩展能力,双端均为 AnyShare 时启用 SAS/信任分级,否则走上游 PIN 流程。
4. 限制执行(FILE_TOO_LARGE/QUOTA_EXCEEDED)仅在 AnyShare 接收端生效,返回上游已定义的 403 语义 + 扩展错误体。
5. 跟踪上游 v3 演进:v2.2 为主目标;v3 稳定后评估迁移(预期为不兼容变更,需独立决策)。

## 6. 上游同步策略

| 项 | 策略 |
|---|---|
| 分支模型 | `main` 跟踪 `upstream/main`(只同步不修改);`anyshare` 长期分支承载品牌+特性;工作分支按 WP 从 `anyshare` 拉 |
| 同步节奏 | 每月评估一次 upstream 变更;安全修复即时同步;rebase 冲突按模块归属处理(我们改动的文件以我们的为准,并重放上游修复) |
| 修改面控制 | 深改集中在新增模块(`app/lib/feature/trust/` 等新目录);对上游文件的修改**最小化**并全部登记 `MODIFICATIONS.md`,降低 rebase 成本 |
| 上游回馈 | 通用性修复(如 Android ROM 兼容、中文翻译)尽量以 PR 回馈上游,减少自有 diff |

## 7. 风险

| 编号 | 风险 | 应对 |
|---|---|---|
| FR1 | 上游重构导致 rebase 成本上升 | 修改面最小化(§6);必要时冻结基线,按安全节奏手动移植 |
| FR2 | 协议 v3 不兼容变更 | 扩展层做版本抽象;v3 稳定前不跟进 |
| FR3 | 商标/品牌混淆引发争议 | 严格替换品牌(§3);README 显著声明 fork 来源;不发上游渠道 |
| FR4 | 上游协议仓库无许可(文档文本) | 不复制其文档文字;实现以主仓库 Apache-2.0 代码与自有实测为准 |
| FR5 | fork 深度依赖上游架构,信任模型侵入面超预期 | Stage 1 先做扩展点设计评审(在代码上定位 PIN/持久化/路由挂点)再动手 |
| FR6 | 上游 Rust CLI(`cli/`)维护负担 | 首版不纳入构建;仅保留 Flutter `app/` 主线 |

## 8. 收益确认(相对自研路线)

- 六端成熟代码(Win/Mac/Linux/Android/iOS/Fire OS)+ 协议互通生态,直接砍掉自研 Stage 1–2 的大部分工作量;
- 性能、稳定性经大规模社区验证(上游分发量千万级),AC-7 基线大概率继承;
- download API 免费获得浏览器接收端(O2);
- 与已确认的技术决策(D1 Flutter)零冲突;
- 我们的精力全部聚焦三个真差异化:鸿蒙、分享集成、信任分级。
