## 1. 产品概述

### 1.1 一句话定位

> 同一局域网内的任意设备之间,不插线、不登录、不走外网,两步把文件传过去。

AnyShare 是一款**跨平台局域网文件互传工具**,覆盖 Windows、Linux、macOS、Android、HarmonyOS 五端。设备打开即自动互相发现,一次配对后即可像"自己的设备"一样随时互传文件,并深度接入微信 / QQ / 系统文件管理器的分享入口。

### 1.2 背景与痛点

| 现有方式 | 痛点 |
|---|---|
| 微信/QQ 传文件 | 需登录、依赖外网、大文件受限、图片视频被压缩、混入聊天记录难整理 |
| 网盘 / 邮件 | 上传+下载两倍时间、空间与大小限制、隐私顾虑 |
| AirDrop | 仅 Apple 生态封闭可用 |
| 华为分享 / 小米互传 / 三星 Quick Share | 各厂商协议封闭,跨品牌、跨桌面系统不可用 |
| U 盘 / 移动硬盘 | 物理插拔麻烦,容易忘带 |
| LocalSend / LANDrop 等开源方案 | 五端里缺原生鸿蒙;与微信/QQ/文件管理器"分享到"链路集成弱,桌面端入口不深 |

**市场空缺**:同时做到「五端互通 + 系统分享入口深度集成 + 无网无账号」的成品目前不存在。

### 1.3 产品目标(可量化)

| 指标 | 目标值 |
|---|---|
| 设备发现速度 | 打开应用后 **3 秒内**列出同网在线设备 |
| 传输吞吐(千兆有线) | ≥ **80 MB/s** |
| 传输吞吐(Wi-Fi 6) | ≥ **50 MB/s**(约为物理速率 60% 以上) |
| 首次配对 | ≤ **2 步操作、30 秒内**完成 |
| 批量发送 | 单次 1000 个文件不卡顿、不失败 |
| 端到端传 100MB | 从分享菜单点"发送"到对端落盘 ≤ 15 秒(千兆环境) |

### 1.4 非目标(明确不做)

- ❌ 不做互联网/广域网传输:无云中继、无账号体系、无服务器成本。
- ❌ 不做文件同步 / 自动备份(历史记录仅作存档)。
- ❌ 不做即时通讯聊天功能(仅支持文本/剪贴板快传)。
- ❌ 首版不分发 iOS(已裁决 2026-10-11):fork 后 iOS 代码随上游免费保留,仅签名分发待 Apple 账号(见 9.2 O1)。
- ❌ 首版不上架任何应用市场:全端 GitHub Releases 自分发(用户仅有 GitHub 账号;华为市场/安卓市场上架列为后续可选)。

## 2. 用户与场景

### 2.1 目标用户

1. **多设备个人用户**:手机 + 电脑 + 平板,日常照片、截图、文档互传。
2. **办公团队**:会议现场把材料从电脑分发到多台手机/电脑,或反向收集。
3. **家庭用户**:手机照片视频批量导入家庭电脑/NAS,免压缩保画质。

### 2.2 核心用户故事

| 编号 | 用户故事 | 涉及能力 |
|---|---|---|
| S1 | 我在 Android 手机文件管理里多选 200 张照片,点"分享 → AnyShare → 我的 MacBook",照片原画质传到电脑 | 系统分享接入、批量传输 |
| S2 | 微信里收到一份 300MB 的 PDF,我"用其他应用打开 → AnyShare",直接发给旁边的电脑 | 微信链路、任意文件类型 |
| S3 | 电脑上我右键一个 8GB 的视频文件夹 →"通过 AnyShare 发送"→ 选手机,手机弹窗确认后自动接收 | 桌面右键、大文件、断点续传 |
| S4 | 同事的电脑第一次连我,发送请求时我确认一次,之后他传文件给我不再打扰 | 配对与信任 |
| S5 | 培训现场,我把课件同时发给 10 台设备 | 一对多 |
| S6 | 传输中途 Wi-Fi 抖动断开 30 秒,恢复后自动续传,不用从头来 | 断点续传、重连 |

## 3. 功能需求

优先级定义:**P0** = 首个可用版本(MVP)必须;**P1** = 第二个版本;**P2** = 远期储备。
需求编号规则:`F-<模块>-<序号>`。

### 3.1 设备发现

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F-DISC-01 | 基于 mDNS/DNS-SD 广播与扫描局域网设备(服务类型 `_anys._tcp.local.`,TXT 记录携带设备名、平台、协议版本、证书指纹) | P0 |
| F-DISC-02 | mDNS 不可用环境(部分路由器禁用组播)的 **UDP 广播兜底**,双通道发现、结果合并去重 | P0 |
| F-DISC-03 | 设备卡片展示:设备名、平台图标、IP、设备类型(手机/电脑)、在线状态 | P0 |
| F-DISC-04 | 在线状态实时感知:设备退出后 10 秒内从列表消失;新设备入网 3 秒内出现 | P0 |
| F-DISC-05 | 网络切换(Wi-Fi ↔ 有线 ↔ 手机热点)后自动重新发现,无需重启应用 | P0 |
| F-DISC-06 | 手动输入 IP:端口添加设备(AP 隔离/跨网段兜底,可达性探测) | P1 |
| F-DISC-07 | 扫码直连:发送端扫码即完成"配对 + 选中该设备"(免滚动查找) | P1 |
| F-DISC-08 | 按平台/名称筛选、收藏设备置顶 | P2 |

### 3.2 配对与信任

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F-PAIR-01 | 首次连接配对:发起方展示 6 位数字 PIN,接收端输入/确认一致后配对成功 | P0 |
| F-PAIR-02 | 配对成功时二选一:**临时传输**(每次传输需确认)或**加入信任列表**(免确认,接收完成时通知提示);信任列表内**同一归属者**的设备自动无限制 | P0 |
| F-PAIR-03 | 未配对设备发来文件:接收端弹窗展示「设备名 + 平台 + 文件清单(名称/大小/缩略图)+ 接受/拒绝」 | P0 |
| F-PAIR-04 | 配对凭据持久化:双端交换公钥指纹,生成共享密钥,后续传输 TLS 双向校验(防中间人) | P0 |
| F-PAIR-05 | 配对数据跨端导出/导入(重装系统后免重新配对) | P2 |
| F-PAIR-06 | 设备管理:重命名(本地备注名)、删除配对、拉黑名单 | P1 |
| F-PAIR-07 | 全局陌生人策略:「需确认」(默认)/「自动接收」;信任分级见 F-PAIR-09~12 | P0 |
| F-PAIR-08 | 扫码配对(与 F-DISC-07 合并为一步) | P1 |
| F-PAIR-09 | 归属者:配对时可标注归属者;**同一归属者**的设备间传输免确认、无任何限制(单文件大小、容量均不受限),等价完全信任 | P0 |
| F-PAIR-10 | 信任分级:信任列表分**一般信任**(可设限制)与**完全信任**(无限制);一般信任限制项 = 单文件大小上限 + 接收容量(绝对值,如 20 GB);配对选「临时传输」的设备不在信任列表,每次确认 | P0 |
| F-PAIR-11 | 限制形式(完全自定义):单文件上限按**绝对值**(如 500 MB)或不限;接收容量按**绝对容量**(如 20 GB)、**磁盘占比**(如 20%)或不限,三项自由组合 | P1 |
| F-PAIR-12 | 限制执行:超限传输被拒并明确提示(含上限值与已用量);占比模式按接收盘总容量实时换算为绝对值执行;已用量为**独立用量账本**(不受历史窗口轮换影响),在设备详情页可**显式重置**以释放配额(2026-10-12 审查修订:原"清理历史释放配额"语义因历史仅保留 30 条不可行,且磁盘占用不因删记录而消失) | P1 |
| F-PAIR-13 | 归属者加入(扫码/邀请码):展示方二维码携带**归属者身份**,新设备扫码后一次操作完成「配对 + 加入我的归属者」,自动进入双方「我的设备」列表(双端确认);解决"我的设备如何自动聚齐"的体验缺口(2026-10-18 补) | P2 |

> F-PAIR-08 落地形态(2026-10-18 补充):**展示方=桌面(或任意设备),扫码方=手机**(摄像头)。展示方生成二维码(含地址/端口/一次性令牌/指纹);扫码方扫码后直接向展示方发起配对注册,双端按现有 SAS 流程确认(或按设置免确认);令牌一次性、60 秒有效。入口:设备列表页「扫码配对」按钮、首次启动引导、我的设备空状态。

### 3.3a 跨设备屏鼠共享(E-2,已立项启动)

> 用户提出(2026-10-12),**2026-10-16 用户裁决立项:两种模式均为正式需求**。
> - **模式 A 边缘穿越**:各设备显示各自内容,键鼠按屏幕空间位置关系跨设备流转(如主设备鼠标越过左边缘 → 出现在左侧设备桌面;类 Barrier/Synergy)。需布局拖拽 UI 与捕获端边缘钩子。
> - **模式 B 虚拟扩展屏**:其他设备屏幕作为主控机的**系统扩展屏**(如 Windows 显示设置中的第二块显示器);技术路线 = 已签名虚拟显示驱动(VDD,MIT)+ DXGI 桌面复制抓帧 + 视频管线串流 + 输入回注。布局即系统显示设置,光标为系统原生行为。
>
> 价值:带屏设备皆可为扩展屏;一套键鼠控制所有设备,免切换连接。联动归属者信任模型(仅同归属者设备可互连)。
>
> **S0 实测完成(2026-10-16)**:Android 无障碍注入(模拟器+真机)、Ubuntu 24.04/GNOME 46 Wayland(RemoteDesktop+InputCapture 双通道 EIS 握手成功;Windows→Ubuntu 注入演示 2500+ 事件全通)、macOS 实验包待跑。详见 [屏鼠共享专项评估.md](./屏鼠共享专项评估.md) 与 docs/E2-S0/。

### 3.5 页面与交互清单

五端保持统一信息架构,共 6 个核心界面:

1. **主页(设备列表)**:顶部本机状态卡(设备名、IP、二维码入口),下方"我的设备"与"附近的设备"两个分组,设备卡片点击 = 选中并进入发送;空态引导。
2. **发送确认页**:文件清单(数量/总大小/缩略图)、选择目标设备(可多选,P1)、发送按钮。
3. **传输进度页/卡片**:总进度 + 分文件进度、速度、剩余时间、取消按钮;完成后变"已发送"态。
4. **接收确认弹窗**:对端信息 + 文件清单 + 接受/拒绝;临时传输与陌生设备需确认;信任列表设备不弹,直接后台落盘 + 完成通知。
5. **历史记录页**:按时间倒序,筛选项(收/发、成功/失败),条目操作(打开/另存/删除记录)。
6. **设置页**:设备名称、归属者、保存路径、陌生人策略、开机自启、语言(中/英)、主题(亮/暗/跟随系统)、日志导出、关于。
7. **设备详情页**(设备卡长按/进入):临时传输 ⇄ 信任列表切换、信任等级(一般信任 / 完全信任)、归属者标注(与我同一归属者 / 其他)、限制设置(单文件上限:绝对值/不限;接收容量:绝对容量 / 磁盘占比 / 不限;同归属者与完全信任恒为"无限制")、重命名、拉黑、删除配对。

交互红线:
- 任何发送路径从"点分享"到"发出"≤ 3 次点击。
- 弱状态提示:所有失败(设备离线、拒绝、校验失败)必须有明确的用户可见反馈与重试入口。

## 5. 技术方案建议(供评审,非强制结论)

### 5.1 总体架构(分层)

```
┌─────────────────────────────────────────────────────┐
│ UI 层(Flutter 统一实现,平台差异化组件按端适配)      │
├─────────────────────────────────────────────────────┤
│ 业务层:设备管理 / 配对信任 / 传输任务队列 / 历史存储    │
├─────────────────────────────────────────────────────┤
│ 协议层:发现(mDNS + UDP 广播) / 传输(HTTPS REST)   │
├─────────────────────────────────────────────────────┤
│ 平台适配层:系统分享接收 / 右键菜单 / 托盘 / 相册写入 / │
│            前台服务 / 防火墙(各端插件)               │
└─────────────────────────────────────────────────────┘
```

### 5.2 UI 框架选型对比

| 方案 | 五端覆盖 | 工作量 | 体验 | 风险 |
|---|---|---|---|---|
| **Flutter(推荐)** | Win/Linux/macOS/Android 官方支持;鸿蒙经华为维护的 flutter_flutter(OpenHarmony 适配) | 低~中(一套代码) | 良好,动效一致 | 鸿蒙适配版落后官方版本约 1~2 个大版本;三方可用的成熟插件需逐一验证 OH 支持 |
| Compose Multiplatform | 无官方鸿蒙;Linux 桌面尚不成熟 | 中 | 良好 | 鸿蒙需社区 port,桌面端短板 |
| React Native(+RN for OpenHarmony) | 桌面弱(需 react-native-windows/macOS 第三方) | 中 | 良好 | 五端拼装感强,维护面大 |
| 各端全原生 | 完整 | 高(≈5 倍) | 最佳 | 成本不可接受 |
| **Tauri/Rust 或 C++ 共享核心 + 各端原生壳** | 完整 | 高 | 好 | 仅在协议层值得复用,UI 不建议 |

**建议结论**:UI 与业务用 **Flutter** 单代码库;传输/发现协议层用纯 Dart 实现保持五端一致;平台能力(分享接收、右键、托盘、相册、前台服务)通过各端插件/平台通道实现;鸿蒙端跟踪华为官方 Flutter-OH 适配,**备选降级方案:鸿蒙端用 ArkTS 原生壳,复用同一套 HTTP 传输协议**(协议与语言无关,降级只影响 UI 层)。

> **v0.4 路线变更**:经用户裁决,本项目改为**基于 LocalSend(Apache-2.0)fork 二次开发**——上述选型作为架构原则继续适用(Flutter/纯 Dart/插件化与上游完全一致);自研协议与 UI 主体取消,以 LocalSend protocol v2.2 为基础做向后兼容扩展。详见 [fork策略与合规.md](./fork策略与合规.md)。

> 参考背书:LocalSend(Flutter)已在 Windows/Linux/macOS/Android 四端验证该技术路线的可行性,AnyShare 的增量主要在「原生鸿蒙」与「系统分享入口深度集成」。

### 5.3 通信协议设计要点

- **发现**:
  - 主通道:mDNS `_anys._tcp.local.`,TXT 记录:`{v:协议版本, name:设备名, device:platform, fp:证书指纹}`。
  - 兜底通道:UDP 端口 53317 广播/组播 JSON 信标(注册、心跳、告别),与 mDNS 结果合并去重。
- **传输**:端到端 HTTPS REST(与 LocalSend v2 协议兼容的风格,便于未来互通):
  - `POST /api/v2/prepare-upload`:发送端声明文件清单,接收端按信任策略返回 `sessionId` 或 401(需配对/确认)。
  - `POST /api/v2/upload?sessionId=...&fileId=...&chunkOffset=...`:分块上传,支持 `Range` 续传。
  - `POST /api/v2/cancel`、`GET /api/v2/info`。
  - 每文件元数据含 `sha256`;目录以 `manifest` 树描述。
- **安全**:自签证书在安装/首启生成;配对时双端展示并交换指纹;已配对设备做证书双向校验。
- **版本化**:协议带 `v` 字段,向后兼容一个版本,降级协商。

### 5.4 各端集成实现要点

| 端 | 要点 |
|---|---|
| Windows | 右键菜单 MVP 用注册表静态动词(`HKCR\*\shell\AnyShare`),把文件路径经命令行/命名管道交给运行中实例;P1 升级 Shell Extension(支持优化多选);Inno Setup 安装时 `netsh advfirewall` 添加入站规则 |
| macOS | App Sandbox + `com.apple.security.network.server/client` entitlement;Quick Action 实现 Finder 右键;Developer ID 签名 + 公证 |
| Android | `intent-filter` 接收 `SEND/SEND_MULTIPLE/VIEW`;`ContentResolver` 读取分享 URI(处理 `content://` 临时权限);前台服务类型 `dataSync`;Android 13+ 细分媒体权限按需申请 |
