## 1. 文档说明

### 1.1 与 PRD 的关系

本文档将 PRD(F-xxx / NF-xxx 编号)细化为可开发的工程方案。每个设计点在「需求追溯矩阵」(第 13 章)中回链 PRD 编号;PRD 开放问题不在此重复决策,涉及处标注 `[依赖 O#]`。

> **v0.4 路线变更(重要)**:经用户裁决(2026-10-11),本项目改为**基于 LocalSend(Apache-2.0)fork 二次开发**,合规与 fork 策略见 [fork策略与合规.md](./fork策略与合规.md)。本设计各章效力:
> - **已被取代**:第 4 章自研协议——实现以 **LocalSend protocol v2.2** 为准(端口 53317、组播 224.0.0.167、prepare-upload/upload/download API),AnyShare 以向后兼容方式扩展(只增不改、未知字段忽略、`/info` 能力协商,见 fork 文档 §5);
> - **继续有效(作为扩展开发依据)**:4.4 信任模型(SAS 配对、4.4.3 判定链)、第 3 章数据模型(trust_level / quota 三模式)、5.3 传输行为要求、第 6 章平台适配(鸿蒙/分享集成)、第 8/10 章错误与安全;
> - D8 修订:默认端口 **53317**(与上游一致、互通优先),被占用时顺延并在发现报文广播实际端口。

### 1.2 设计原则

1. **协议优先**:发现/配对/传输协议与 UI 框架解耦,纯文本协议(JSON over TLS),任何端可独立实现。
2. **一套核心,薄端适配**:业务逻辑 100% 在共享层(Flutter/Dart),平台代码只做「系统入口 + 系统能力」。
3. **默认安全**:全链路 TLS,配对防中间人,私钥不出沙箱。
4. **可降级**:mDNS 失败走 UDP 广播,Flutter-OH 受阻走 ArkTS 壳(见 6.2.6)。

### 2.3 进程与线程模型

#### 2.3.1 进程模型

| 端 | 模型 |
|---|---|
| Windows/macOS/Linux | 单进程单实例;窗口关闭 = 隐藏到托盘;第二个实例启动时经 IPC 把参数移交已有实例后退出 |

#### 2.3.2 Dart Isolate 模型(Flutter 各端一致)

| Isolate | 数量 | 职责 |
|---|---|---|
| main | 1 | UI、业务编排、REST 客户端(发送方向) |
| server | 1 | HttpApiServer + UDP beacon 收发 + mDNS 应答(RawDatagramSocket 组播) |

## 3. 核心数据模型

### 3.1 领域对象(关键字段)

```dart
/// 发现到的设备(在线缓存,不落库)
class DeviceEndpoint {
  final String deviceId;      // UUID v4,设备唯一标识(重装即新设备)
  final String name;          // 自报设备名
  final DevicePlatform platform; // windows|macos|linux|android|harmonyos
  final String certFingerprint; // SHA-256 hex(64)
  final List<InternetAddress> addresses; // mDNS 来源地址 + TXT 内地址
  final int port;             // HTTPS 端口,默认 53318
  final int protoVersion;     // 协议版本,当前 1
  final DateTime lastSeen;
  DeviceState state;          // seen(<3s) / stale(3~10s) / gone(>10s)
}

/// 已配对设备(持久化)
class PairedDevice {
  final String deviceId;
  String alias;               // 本地备注名
  final String certFingerprint; // 信任锚:证书变更 = 需重新配对
  final String publicKeyPem;  // 身份公钥(配对时交换)
  final DevicePlatform platform;
  bool favorite, blocked;
  final String ownerId;       // 归属者 ID(对端自报,配对时交换;4.4.3)
  String ownerName;           // 归属者显示名
  TrustLevel trustLevel;      // temp(临时)| limited(一般)| full(完全)
  DeviceLimits? limits;       // 一般信任的限制;full/temp 恒为 null
  final DateTime pairedAt;
}

/// 信任等级(v0.3 用户裁决:配对时二选一,加入信任列表后选等级)
enum TrustLevel { temp, limited, full }

/// 一般信任的限制(三项自由组合,完全自定义)
class DeviceLimits {
  final int maxFileSize;      // 单文件大小上限(字节);0 = 不限
  final QuotaSpec quota;      // 接收容量限制
}

/// 容量限制三模式(v0.3 用户裁决)
class QuotaSpec {
  final QuotaMode mode;       // none | absolute | percent
  final int value;            // absolute:字节;percent:万分比(2000 = 20%)
}

/// 待传输文件元数据(协议 DTO,同时用于 UI 展示)
class FileMetaDto {
  final String fileId;        // 会话内唯一,"1","2",...
  final String relPath;       // 相对根路径,如 "photos/IMG_01.jpg";根路径文件仅文件名
  final int size;             // 字节
  final String sha256;        // 发送端预计算(小文件)或流式计算(大文件)
  final int? mtime;
}

/// 传输任务(UI 与持久化共用)
class TransferTask {
  final String id;            // 本地 UUID
  final String? sessionId;    // 对端分配(接收方向必有)
  final TransferDirection direction; // send | receive
  final String peerDeviceId;  // 可为空(未配对一次性传输)
  final String peerName;
  final List<TransferFileItem> files;
  final int chunkSize;        // 协商结果,默认 4 MiB
  TransferStatus status;      // 见 5.3.1 状态机
  final int createdAt;
}
```

## 4. 协议详细设计

协议名 **AnyShare Protocol v1**。独立规范文档将落在 `docs/协议规范.md`,本章为设计定稿。

### 4.1 端口与端点

| 项 | 值 |
|---|---|
| TCP(HTTPS/REST) | **53318**(默认;被占用时 53318–53338 顺延,实际端口写入发现信令) |
| UDP(beacon) | **53318**(固定,广播 + 组播 239.255.53.31) |
| mDNS 服务类型 | `_anys._tcp.local.` |
| URL 前缀 | `https://<host>:<port>/api/anyshare/v1/` |

### 4.2 设备发现协议

#### 4.2.1 mDNS 通道(F-DISC-01)

注册服务 `_anys._tcp.local.`,TXT 记录:

| key | 必填 | 示例 | 说明 |
|---|---|---|---|
| `v` | ✅ | `1` | 协议版本 |
| `id` | ✅ | `8f2c…` | deviceId |
| `name` | ✅ | `My MacBook` | UTF-8,≤64 字节,`=`/`;` 转义 |
| `device` | ✅ | `macos` | 平台枚举 |
| `fp` | ✅ | `a3b1…`(64 hex) | 证书 SHA-256 指纹 |
| `oid` | ✅ | `0d7e…` | 归属者 ID(4.4.3) |
| `owner` | ❌ | `张三` | 归属者显示名(UTF-8 转义同 name) |
| `port` | ❌ | `53320` | 与 mDNS 端口不同时必填 |

启动即注册;活跃查询周期 30 s(事件驱动为主,轮询兜底);退出/休眠前发 mDNS Goodbye(`TTL=0` 注销)。

#### 4.2.2 UDP beacon 通道(F-DISC-02)

信令为单行 UTF-8 JSON,广播地址 `255.255.255.255:53318` + 组播 `239.255.53.31:53318`:

```json
// 周期信标(每 5s)+ 网络变化立即发送
{"proto":1,"id":"uuid","name":"My MacBook","device":"macos",
 "fp":"a3b1…","oid":"0d7e…","owner":"张三","port":53318,"ts":1760000000000}
// 探测请求(进入前台/下拉刷新时单播广播各一次,触发对端立即回信标)
{"proto":1,"probe":true,"id":"uuid"}
// 退出告别
{"proto":1,"id":"uuid","bye":true}
```

规则:
- 同 `id` 的 mDNS/beacon 结果按 `id` 去重合并进 `DeviceRegistry`,地址取并集。
- 收到 `probe` 后 100 ms 内回信标(加随机抖动 ±50 ms 防风暴)。
- `ts` 偏差 > 120 s 的信标忽略(防重放陈旧数据);信标不含任何敏感字段。
- beacon 载荷不签名——它只用于"发现",身份认证一律在 TLS + 指纹层完成。

#### 4.2.3 在线状态机(F-DISC-04)

```
seen ──(3s 无心跳)──> stale(列表置灰)──(再 7s)──> gone(移除,发 Bye 补偿)
  ↑ 收到任意信标/连接活动即回到 seen
```

新设备入网 ≤ 3 s 出现:靠 probe 触发对端即时回包;被动等待上限即信标周期 5 s,满足 PRD。

### 4.3 安全模型(NF-S1/S2)

| 项 | 设计 |
|---|---|
| 身份 | 每实例首启生成 **ECDSA P-256** 自签证书,`CN=<deviceId>`,有效期 10 年 |
| 指纹 | `SHA-256(DER 证书)` hex 展示;配对后持久化为信任锚 |
| TLS | TLS 1.2+(强制 1.3 优先),双向认证可选;已配对设备**必须**校验对端证书指纹,不匹配即断开并提示"设备身份变更" |
| 未配对首连 | `TOCTOU` 防护:TLS 建立后取对端 `/info` 指纹与发现信令中 `fp` 比对,一致才进入配对 |
| PIN 防爆破 | 配对注册接口按来源 IP 限速 5 次/分钟,超限 429 + 锁 60 s(NF-S2) |

### 4.4 配对协议(SAS 数字比对)

采用 **ZRTP 风格 SAS(Short Authentication String)**:双端展示同一组 6 位数字,用户肉眼比对后各自点「一致」,防中间人(MITM 无法推导出双方一致的安全信道密钥,猜中概率 10⁻⁶/次)。对应 F-PAIR-01/04/08。

#### 4.4.1 报文与派生

```
A(发起方)                                   B(接收方)
│ POST /pair/register                       │
│ {A_id,A_name,A_device,A_fp,A_pub,         │
│  A_oid,A_owner,A_eph_pub, proto:1}        │
│──────────────────────────────────────────>│ B 生成 B_eph 私钥,入 pending 表(TTL 120s)
│                                           │
│        {B_id,B_name,B_device,B_fp,B_pub,  │
│         B_oid,B_owner,B_eph_pub,          │
│         salt, ttlMs} <────────────────────│ 响应 200
│                                           │
│ 双方:K = HKDF-SHA256(ECDH(A_eph,B_eph),   │
│        salt, info="anys-sas-v1", 32B)     │
│ 双方:SAS = HMAC-SHA256(K,"sas")[0..3]     │
│        → 大端 uint32 → % 1_000_000        │
│        → 6 位十进制(前导零保留)           │
│                                           │
│  [A 屏幕:0 4 2 7 1 3]      [B 屏幕:0 4 2 7 1 3]   ← 用户比对
│                                           │
│ POST /pair/confirm {} (A 用户点"一致") ───>│ B 收到且 B 用户已点"一致"(或随后点击)
│ <──────────────────── 200 {paired:true} ──│ → 双方写 devices 表(信任锚=对方 fp)
```

- ECDH 用**临时**密钥对(X25519 或 P-256,与身份证书分离),配对完成后即丢弃,前向保密。
- 任一端点「不一致」→ `POST /pair/abort`,双方清 pending,UI 明确警告"可能存在中间人,请检查网络"。
- 确认序宽容:先收到对端 confirm 的一方进入 `confirmedWaitingPeer`,本地用户再点即完成;TTL 120 s 内未完成自动作废。
- 扫码直连(F-PAIR-08/F-DISC-07):二维码内容 `anyshare://pair?ip=192.168.1.8&port=53318&fp=a3b1…&id=uuid`,扫码端校验 `fp` 后直接进入上述流程,并跳过设备列表选中步骤。
- **配对完成后的选择(F-PAIR-02,v0.3 用户裁决)**:SAS 双确认落库时记录对端 `ownerId/ownerName`,本端随即二选一:
  ① **临时传输**(`trust_level = temp`):身份已验证、留有记录,但每次传输仍弹确认;
  ② **加入信任列表**:免确认接收、完成时通知提示;加入时选等级——**完全信任**(`full`,无任何限制)/ **一般信任**(`limited`,可设单文件上限与容量限制)/ 或直接标注**同归属者**(对端 ownerId == 本机 ownerId,等价完全信任)。
  选择与限制随时可在设备详情页(7.1)修改,仅影响本端判定;`ownerId` 匹配判定发生在本地信任视图,不修改任何一端的自报身份。

#### 4.4.2 配对状态机(单端视角)

```
idle → registered(收到/发出 register,TTL 内)
     → sasShowing(双方显示 6 位数字)
     → confirmedLocal / confirmedPeer(先后无序)
     → paired(双确认,持久化)
     → postPairChoice(临时传输 / 加入信任列表+等级;跳过 = 临时)← v0.3 修订
     任一步:abort / expired(120s)→ idle
```

#### 4.4.3 信任模型与判定链(v0.3,D4 用户裁决定稿)

配对(SAS)成功后的本端选择决定对端信任档位;接收端在 `prepare-upload` / `text` 到达时,按对端**证书指纹**(唯一信任锚)执行以下判定:

```
输入:fingerprint(来自 TLS 对端证书,不可伪造)
  │
  ├─ 0. devices.blocked = 1                → 拒绝(403 BLOCKED)
  ├─ 1. 未配对(指纹不在 devices 表)
  │     ├─ strangerPolicy = ask(默认)     → 挂起等待用户确认(30s 超时 408)
  │     └─ strangerPolicy = autoAccept     → 自动接受(无限制)
  ├─ 2. 已配对 && peer.ownerId == 本机.ownerId
  │                                        → 【同归属者】免确认,无任何限制 ★
  ├─ 3. 已配对 && trust_level = full       → 【完全信任】免确认,无限制
  ├─ 4. 已配对 && trust_level = limited    → 【一般信任】免确认,适用限制(下表)
  └─ 5. 已配对 && trust_level = temp       → 【临时传输】每次挂起等待用户确认
```

**一般信任的限制定义**(仅第 4 级生效;同归属者与完全信任恒为无限制):

| 限制项 | 形式 | 说明 |
|---|---|---|
| 单文件上限 `maxFileSize` | 绝对值;0 = 不限 | 拒绝时附被拒文件清单 |
| 接收容量 `quota` | **三选一**:`none`(不限)/ `absolute`(绝对容量,字节)/ `percent`(磁盘占比,万分比) | 占比模式按下载盘总容量实时换算:`上限 = total × quota_value / 10000`;设置界面同步显示换算后的绝对值 |

**限制执行**(在 prepare 阶段、生成 sessionId 之前;已用量口径见 3.2):

1. 任一 `files[].size > maxFileSize` → 403 `{"code":"FILE_TOO_LARGE","maxFileSize":N}`,并附"被拒文件清单"供 UI 展示;
2. `已用容量 + 本次总大小 > 容量上限` → 403 `{"code":"QUOTA_EXCEEDED","quota":N,"used":M}`(占比模式 `quota` 为换算后绝对值,附 `quotaPercent` 原始占比);
3. 通过 → 正常发放 sessionId(与 4.5.3 一致)。

接收完成提示:信任列表设备(第 2/3/4 级)接收完成后发系统通知(F-INT-R3);临时传输与陌生人本就有确认交互,不重复打扰。UI 侧徽标:同归属者「· 我的设备」、完全信任「· 完全信任」、一般信任「· 受限」、临时「· 临时」。发送端收到上述 403 时给出明确文案(限额调整需接收端用户在设备详情页操作,无远程申请通道——避免提权攻击面)。

```json
{"error": {"code": "PIN_LOCKED", "message": "尝试次数过多,请 60 秒后重试"}}
```

#### 4.5.1 API 总表

| 方法 & 路径 | 方向 | 用途 |
|---|---|---|
| `GET /info` | 任何人 | 设备信息与能力(发现后首查) |

#### 4.5.2 `GET /info`

```json
{
  "proto": 1, "deviceId": "uuid", "name": "My MacBook",
  "device": "macos", "fingerprint": "a3b1…",
  "ownerId": "0d7e…", "owner": "张三",
  "downloadDirName": "Downloads",
  "maxFileBytes": 10995116277760       // 10 TiB 上限保护
}
```

#### 4.5.3 `POST /prepare-upload`

请求:

```json
{
  "proto": 1,
  "sender": {"deviceId":"uuid","name":"Pixel 8","device":"android",
             "fingerprint":"…","ownerId":"0d7e…","owner":"张三"},
  "files": [
    {"fileId":"1","relPath":"photos/IMG_0001.jpg","size":4096152,"sha256":"…","mtime":1759970000},
    {"fileId":"2","relPath":"docs/报告.pdf","size":330000000,"sha256":"…"}
  ]
}
```

接收端处理(F-PAIR-03 / F-XFER-06):
1. 按 **4.4.3 判定链**执行:黑名单 → 拒绝;同一归属者 / 信任归属者 / 信任设备 → 自动接受(先过限制检查,见 4.4.3);已配对未信任或未配对 → 弹确认框,**HTTP 请求挂起等待用户**(挂起上限 30 s,超时 408)。
2. 重名检查(按 conflictStrategy):重命名时最终路径在响应中给出;`skip` 的文件返回 `skipped`(F-XFER-15 差量跳过:已存在且 SHA-256 一致直接 `skipped`)。
3. 断点续传:存在 `<sha256>.part` 且 size 匹配 → 该文件返回 `offset = received`(F-XFER-08)。

响应:

```json
{
  "sessionId": "b6d4…", "expiresAt": 1760000900000,
  "chunkSize": 4194304,
  "files": [
    {"fileId":"1","status":"pending","offset":0,"saveName":"IMG_0001.jpg"},
    {"fileId":"2","status":"pending","offset":62914560,"saveName":"报告.pdf"},
    {"fileId":"3","status":"skipped"}
  ]
}
```

拒绝:403 `{"code":"REJECTED"}`;未配对且用户拒绝同 403。**403 前后 UI 均有明确反馈**(F-PAIR-03、交互红线)。

#### 4.5.4 `POST /upload?sessionId=…&fileId=…&offset=…`

- Body 为原始字节,`Content-Type: application/octet-stream`,必带 `Content-Length`。
- 每块 ≤ 协商 `chunkSize`(最后一块可小)。`offset` 必须等于接收端当前已收字节数,否则 409 `{"code":"OFFSET_MISMATCH","expected":N}`(发送端据此纠偏续传)。
- 接收端行为:追加写 `<sha256>.part` → 更新 `.meta` → 增量喂给 hash-worker。文件收满时:
  - SHA-256 一致 → fsync → 原子 rename 到最终路径(F-XFER-07)→ 响应 204;
  - 不一致 → 删除 `.part` → 422 `{"code":"CHECKSUM_FAILED"}`,发送端对该文件**整文件重传一次**(F-XFER-05),再失败标记会话 failed。
- 会话不存在/过期:404 `SESSION_NOT_FOUND`。会话 TTL:无活动 10 分钟过期。

#### 4.5.5 `POST /text`

```json
{"proto":1,"sender":{…同上…},"text":"https://example.com/x","previewOnly":false}
```
确认语义与 prepare-upload 相同(挂起等用户);接收端通知栏展示 + 一键复制,不入历史库文件表(历史表 `rel_path` 记为 `@text`)。

#### 4.5.6 `POST /cancel`

`{"sessionId":"…","reason":"user|error:…"}`;接收端清理 `.part` 与会话;双向可用(发送端/接收端 UI 的取消按钮,F-XFER-04)。

#### 4.5.7 版本协商与兼容

- `proto` 不匹配时:高版本端按 `min(both)` 降级;无法满足 → 响应 400 `{"code":"PROTO_UNSUPPORTED","supported":[1]}`。
- 未知字段一律忽略(前向兼容);新增必填字段必须升 minor 并保证旧端可降级运行。

## 5. 模块详细设计

### 5.1 DiscoveryService

**职责**:维护本机信标(mDNS 注册 + UDP 心跳),聚合双通道远端设备,输出 `Stream<List<DeviceEndpoint>>`。

```
启动:  off → probing(发 probe,监听 2s) → online
事件:  网络变化(平台通道 onNetworkChanged)→ rebind(重绑 socket,重新注册 mDNS,回 probing)
关闭:  online → bye(发 Goodbye+UDP bye) → off
```

实现要点:
- `RawDatagramSocket.bind(any, 53318, reuseAddress: true, reusePort(仅Linux/mac))`,joinGroup 组播地址。
- 设备表:`Map<deviceId, DeviceEndpoint>`,定时器 1 s tick 驱动状态机(4.2.3),状态变更即向 UI 推送新快照。
- Android 后台限制:mDNS 在 app 进入后台被 ROM 冻结时,信标由前台服务期间的 socket 保持;完全杀进程则依赖对端 probe 发现不到——属预期(手机端"可被发现"即前台可见)。
- 手动添加(F-DISC-06,P1):`DeviceEndpoint` 手工注入 + 周期 TCP `GET /info` 可达性探测(10 s 间隔,3 次失败置 offline)。

### 5.2 TrustManager / PairingFlow

**TrustManager**:证书加载/生成(首启)、指纹计算、`devices` 表 CRUD、黑名单、信任列表与归属者判定(4.4.3 判定链)、配额缓存维护与限制执行(3.2,含占比换算)。

**PairingFlow** 状态机见 4.4.2;负责 register/confirm/abort 三接口的客户端与服务端编排、SAS 展示回调到 UI、双确认后写库。

### 5.3 TransferEngine

#### 5.3.1 传输任务状态机

```
queued → preparing(调 prepare-upload)
      → waitingConfirm(对端用户确认中,UI 显示"等待对方接收")
      → transferring → finalizing(尾块校验/原子重命名) → completed
任意态 → cancelled(本端) / rejected(403) / failed(网络/校验/存储)
waitingConfirm → expired(408)
transferring 中断连 → retrying(≤3 次,指数退避 1s/4s/16s)
  → 重连成功:按 offset 续传;3 次失败 → failed(任务保留,.part 保留,可手动"继续")
```

#### 5.3.2 发送流水线(F-XFER-02/NF-P1)

单文件内**分块串行、读写与哈希并行**;多文件按 `maxConcurrency=2` 并行(独立 TCP 连接,同一 sessionId):

```
FileReadStream(4MiB buffer)
   │ chunk
   ├──────────────> hash-worker isolate ──(增量摘要)
   │                        │
   └──> TLS HttpClient.send(upload) ──> 读响应
        (offset=已确认字节数,含 409 纠偏重试)
```

- 大文件 sha256 在 prepare 前逐文件流式预计算(4 MiB 增量,同 worker 池);10 GB 文件预计算 ≈ 30–60 s(_NVMe_),期间 UI 显示"准备中(第 n/N)"——大文件哈希对断点续传与差量跳过是必需成本,可接受。
- 速度优化:关闭代理(`HttpClient.findProxy = false`)、`noDelay`、连接按 fileId 复用。

#### 5.3.3 接收流水线

```
TLS chunk → 增量 hash-worker ┐
           ├→ 追加写 .part → 更新 .meta(fsync 每 chunk)
收满:比对 sha256 → fsync → rename 到最终路径 → 通知/历史
```

- 落盘目录冲突即时重命名(`name(1).ext`,循环探测,上限 9999)。
- 磁盘剩余空间预检:prepare 时若 `< 总大小 × 1.02` 直接 507 `{"code":"INSUFFICIENT_SPACE"}`。

### 5.4 ResumeManager

- `.part` 命名以 `sha256` 为键 → 跨 sessionId/跨重启可续(F-XFER-08、NF-R3)。
- `.meta` 写入采用「写临时 + rename」防半写。
- 发送端重试/继续:`prepare-upload` 响应的 `offset` 跳过前 N 字节(`FileReadStream` seek)。

### 5.5 HistoryRepository / NotificationGateway / SettingsService

- HistoryRepository:transfers/transfer_files 表封装;「打开文件」按端调用平台打开;「清空」= 删除记录(不删已接收文件);保留上限 1000 条(超出滚动删除,可配置关闭上限)。
- NotificationGateway:统一 `notifyProgress/notifyDone/notifyText/notifyConfirm` 抽象;桌面走系统通知插件,移动走通知栏 channel(`transfer`/`pairing` 两个 channel);点击通知深链 `anyshare://transfer/<id>`。
- SettingsService:`settings` 表 KV + 内存缓存 `ValueNotifier`;设置变更广播(如 deviceName 变更 → 重发信标)。

```json5
}]
"requestPermissions": [
  { "name": "ohos.permission.INTERNET" },
  { "name": "ohos.permission.GET_NETWORK_INFO" }
]
```

## 9. 性能设计(NF-P1~P4)

| 项 | 措施 |

| 吞吐 | 4 MiB chunk 串行流水(读/哈希/写并行);TCP_NODELAY;每文件单连接复用;千兆理论瓶颈 ≈ TLS 加解密,P-256 握手后会话密钥 AES-GCM 硬件加速,目标 ≥ 80 MB/s |

## 10. 安全设计汇总

### 10.1 威胁模型与对策

| 威胁 | 对策 |
|---|---|
| 局域网窃听 | TLS 1.2+ 全流量加密 |
| 中间人(首次连接) | SAS 数字比对(4.4),MITM 成功概率 10⁻⁶/次且用户可感知 |
| 证书替换(配对后) | 指纹信任锚,变更即断 + 强警示 |
| 恶意设备骚扰 | 信任策略默认陌生人需确认;register 限速;黑名单 |
| 伪造信标 | 信标仅提供"存在性",收发必经 TLS + 指纹认证 |
| 归属者冒充 | `ownerId` 为自报属性、非密码学身份;免确认的前提是**已配对且证书指纹匹配**(4.4.3 信任列表各级与同归属者判定),伪造相同 ownerId 的陌生设备仍走确认流程;限制调整无远程申请通道,防提权 |
| 空间耗尽 DoS | prepare 阶段磁盘预检 + 10 TiB 上限 + 未确认会话不落盘 |
| 路径穿越攻击 | `relPath` 白名单校验:拒绝绝对路径、`..`、空段、Windows 保留名(`CON/PRN/…`)、控制字符;`save_path` 由**接收端**拼接,不信任发送端任何路径 |
| 超大元数据 DoS | 请求体上限 1 MiB,files ≤ 5000 项,relPath ≤ 512 B |

### 10.2 隐私红线

零遥测、零崩溃上报(NF-S3);历史仅本地;权限最小化(NF-S5,不申请通讯录/短信/位置);网络权限范围:仅监听/连接 RFC1918 与链路本地地址段(设置中「允许连接任意内网 IP」默认开、公网地址默认拒)。

### 10.3 密钥保护分级

| 级 | 端 | 方案 |
|---|---|---|
| P0 | 全部 | 应用数据目录 + 文件权限 600(移动端天然沙箱) |
| P1 | Android | Android Keystore(StrongBox 可用则启用)包裹 CEK,私钥加密存储 |
| P1 | 鸿蒙 | HUKS 密钥导入/生成 |
| P1 | macOS | Keychain 存私钥 |
| P2 | Windows | DPAPI;Linux libsecret(无则回退文件权限) |

## 14. 关键技术决策记录(ADR 摘要)

| # | 决策 | 理由 | 备选与否决原因 |
|---|---|---|---|
| D1 | UI/业务 Flutter 单代码库;协议纯 Dart(**用户已确认 2026-10-11**) | 5 端一致性与成本;LocalSend 已验证;AI 单人开发成本最低 | Compose MP 无鸿蒙;全原生 5 倍成本 |
| D2 | 传输 HTTPS REST + mDNS/UDP 发现(**用户已授权 2026-10-11**) | 实现简单可调试、易与 LocalSend 类协议互通(O3) | QUIC/自研 TCP——生态差、穿透无收益(无广域网目标) |
| D3 | 配对用 SAS 双显数字而非单端输 PIN(**用户已同意 2026-10-11**) | 等价安全下交互更少;ZRTP 成熟范式 | 明文传 PIN(依赖 TLS 但首连无锚,弱) |
| D4 | `prepare-upload` 阻塞等待接收方确认;**信任模型(用户裁决 v0.3)**:配对时二选一——「临时传输」(每次确认)或「加入信任列表」(免确认,完成通知);信任列表分**一般信任**(可设单文件上限 + 容量限制:绝对值/磁盘占比/不限)与**完全信任**(无限制);**同归属者**设备等价完全信任 | 免轮询/回调打洞;配对意图显式化(临时 or 信任);限制三模式满足完全自定义需求 | 长轮询/回调——复杂;"配对即完全信任"——粒度不足;"配对即免确认"——弱化配对语义(用户已明确改判) |
| D5 | `.part` 以 sha256 命名(**用户已授权**) | 跨会话/跨重启续传 | sessionId 命名——发送端重启即失效 |
| D6 | Android 不复制分享文件、直读 URI 流(**用户已同意**) | 大文件零拷贝 | 全量复制缓存——8 GB 视频不可接受;取舍见 6.1.2 |
