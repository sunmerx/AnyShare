# 串流数据面加密(AES-256-GCM)与密钥分发阻塞项

> 自包含文档。仓库 `E:\code\AnyShare`,分支 `anyshare`;组件 `packages/screen-stream`(Rust 串流引擎)、
> `app`(Flutter 客户端)、`packages/localsend_isolates`(Dart↔Rust 桥)。

---

## 1. 威胁模型:为什么需要加密

屏幕内容以 H.264 码流通过 **UDP** 在局域网内传输。UDP 本身无加密,任何与发送端/接收端
处于同一广播域(同一 Wi-Fi、同一交换机端口镜像、或能 ARP 欺骗的机器)都能:

- 嗅探到完整的屏幕画面(包含密码输入、聊天记录、内网文档);
- 注入伪造的 H.264 包,在接收端显示任意画面;
- 篡改包头(帧号/序号)造成花屏或拒绝服务。

文件传输走的是 Rust 核心的 HTTPS(双向证书),**而屏幕码流此前是明文**。本文档记录为其
引入的加密机制、当前状态与阻塞项。

---

## 2. 协议设计

### 2.1 包结构(不改变线格式)
每个 UDP 包仍然是 30 字节明文头 + 负载:

| 偏移 | 长度 | 字段 | 是否加密 | 是否认证(AAD) |
|---|---|---|---|---|
| 0 | 4 | magic | 明文 | 是 |
| 4 | 2 | version | 明文 | 是 |
| 6 | 1 | flags(关键帧/不连续/头/FEC) | 明文 | 是 |
| 7 | 1 | 保留 | 明文 | 是 |
| 8 | 4 | session | 明文 | 是 |
| 12 | 4 | frame_id | 明文 | 是 |
| 16 | 2 | seq | 明文 | 是 |
| 18 | 2 | count | 明文 | 是 |
| 20 | 8 | timestamp | 明文 | 是 |
| 28 | 2 | payload_len | 明文 | **仅长度校验** |
| 30 | N | payload(H.264 分片) | **AES-256-GCM 密文** | — |

- 头部保持明文的原因:接收端必须能**在解密前**完成会话识别、帧号排序、NACK 判定与 FEC 分组。
- 头部被当作 **AAD**(附加认证数据)参与 GCM 认证:攻击者改动 session/frame_id/seq/flags/timestamp
  都会导致 tag 校验失败,包被丢弃。
- `payload_len` 不进 AAD 是安全的:它只是"缓冲区里有多少字节",任何截断/追加都会使 GCM
  tag 失配(实现里 `Packet::decode` 还会按该长度校验缓冲区边界,不足即判无效)。

### 2.2 nonce 构造(唯一性论证)
GCM 要求 **同一密钥下 nonce 绝不重复**,否则可恢复明文与认证密钥。本实现:

```
nonce(12B) = session(4, LE) || frame_id(4, LE) || kind_seq(4, LE)
kind_seq   = seq                      (数据包)
           = 0x8000_0000 | seq        (FEC 校验包,seq 是该块的块索引)
```

- 同一会话内 `(frame_id, kind_seq)` 唯一:一个帧号对应一个访问单元(AU);FEC 包用最高位
  与数据包区分。
- **重传**:NACK 重传发送的是**同一份密文**,即"同 nonce + 同明文",对 GCM 安全(输出相同)。
- **数据包 seq 上限**:nonce 用最高位区分 FEC,因此要求数据包 `seq < 0x8000`(32768)。
  `packetize` 里加了断言:编码器输出上限 8 MiB ≈ 7000 包,远低于该阈值;该断言只用于兜住
  未来的实现错误,避免 keystream 复用。
- **会话重启**:每个共享会话使用一把**新密钥**,因此即使 nonce 相同也无害。

### 2.3 密钥分发(当前状态:**未启用**)
设计上:发送端在发起共享时生成 32 字节随机密钥,经**已验证身份的控制通道**交给接收端。

**当前实现的关键阻塞**:应用的控制面(端口 53318,承载 `/screen/offer`、`/screen/accept`、
`/screen/stop`、`/screen/keyframe`、`/screen/bitrate`)是**明文 HTTP**。若在这条通道上传密钥,
同网段的嗅探者可以直接拿到密钥并解密整条 UDP 流 —— 加密形同虚设。

因此本轮的处理是:

1. **Rust 引擎已实现并测试完整 AES-256-GCM 数据面加密**(可用命令行显式开启,见 §4);
2. **应用默认不启用**(不发送密钥、不解密),保持与对端一致的明文行为;
3. 启用前提是控制面改为 **TLS(双向证书 + 对端证书指纹校验)**,已列为安全待办第一项;
   届时只需在 offer 里恢复携带密钥、并把 `keyHex` 传给引擎,Dart 侧代码路径已就绪
   (`startSender(keyHex:)` / `startReceiver(keyHex:)`,当前只传 `null`)。

> 明确结论:**在控制面 TLS 落地之前,本实现不提供实际的机密性/完整性保护**。
> 代码存在的意义是把密码学部分做完并验证,避免把"安全"留成一句空话。

## 3. 代码位置
- `packages/screen-stream/src/transport.rs`
  - `SESSION_KEY_LEN`/`AEAD_TAG_LEN`;`cipher_from_key(&[u8]) -> Option<Aes256Gcm>`;
  - `seal_packet(&mut Packet)` / `open_packet(&mut Packet)`(原地加解密,头部作 AAD);
  - `Packet::header_bytes()`(与 `encode()` 共用,避免每包重复分配);
  - `packetize` 的 `data_count <= 0x7fff` 断言;
  - 单测:`sealed_payload_roundtrips_and_detects_tampering`(密文篡改/头部篡改/错密钥/长度校验)、
    `nonce_differs_for_data_parity_and_frames`。
- `packages/screen-stream/src/sender.rs`
  - `SenderConfig.session_key: Option<[u8; 32]>`;
  - `encode_packets(packets, cipher)` 统一加密(含 SPS/PPS 头包与 **shutdown 尾包**);
  - 启动日志打印 `data plane encryption = AES-256-GCM / OFF (plaintext)`。
- `packages/screen-stream/src/receiver.rs`
  - `ReceiverConfig.session_key`;`receive_loop` 在 `Packet::decode` 后解密,失败计入
    `auth_fail` 并丢弃;统计日志新增 `auth_fail=`。
- `packages/screen-stream/src/bin/ss-send.rs` / `ss-view.rs`
  - 密钥从**环境变量 `ANYSHARE_KEY`**(64 位十六进制)读取,**不接受命令行参数**
    (命令行会进入 shell 历史、进程审计与其他用户的 `ps` 输出)。
- `packages/localsend_isolates/rust/src/api/screen.rs`
  - `start_screen_sender(..., key_hex)` / `start_screen_receiver(port, key_hex)`;
    `parse_session_key` 对**非空但非法**的密钥返回**错误**(fail-closed,绝不静默降级明文);
    空串表示"显式不加密"(仅命令行/调试用途)。

## 4. 如何验证(命令行,单机或双机)

密钥(64 位十六进制):
```bash
KEY=00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff
```

接收端(Linux,需 X 显示):
```bash
ANYSHARE_KEY=$KEY ~/e2/anyshare/target/release/ss-view --port 53319 \
  --ffmpeg-path ~/ffmpeg-7.0.2-amd64-static/ffmpeg
```
发送端(Windows):
```powershell
$env:ANYSHARE_KEY = "00112233445566778899aabbccddeeff00112233445566778899aabbccddeeff"
& E:\code\AnyShare\target\release\ss-send.exe --target <linux-ip>:53319 --seconds 10
```

预期:发送端日志 `data plane encryption = AES-256-GCM`;接收端正常出画,
`recv: delivered=… auth_fail=0`。

**负向验证**(仅接收端带密钥、发送端不带):接收端 `delivered=0`、`auth_fail` 持续增长,
画面不出现。本项目实测:6 秒内 `auth_fail` 由 760 增至 2028。

## 7. 已知限制与待办
1. **阻塞项(最高优先)**:控制面 TLS。需把 53318 改为 `HttpServer.bindSecure`(强制客户端
   证书),客户端用 `HttpClient` 携带本机证书并以**对端证书指纹**校验服务端;随后 offer 恢复
   携带密钥。完成前,应用保持明文(见 §2.3)。
2. **重放/会话绑定**:`session` 在头部但不参与密钥派生;若同一密钥被重复使用(命令行场景),
   录制的旧会话可被重放。应用侧每会话使用新密钥,因此不受影响;如需在命令行场景加固,
   可按 `KDF(key, session)` 派生子密钥(需要引入 HKDF)。当前记为已知限制。
3. **控制面身份**:`/screen/offer` 目前信任请求体里的 `fingerprint` 字段;接入 TLS 后应改为
   从连接证书派生对端指纹(与核心 Rust HTTP 服务的 `certFingerprint` 一致),不再信任自述字段。
4. **密钥清零**:Rust 侧密钥保存在 `SenderConfig/ReceiverConfig` 中,生命周期与会话一致;
   未做显式内存清零(zeroize)。在桌面进程模型下属可接受,记为待办。
5. **失败可观测性**:认证失败目前只在 `recv:` 统计行里计数;尚未转成 `StreamEvent::Error`
   给用户可见提示(表现为黑屏 + 日志)。待控制面 TLS 启用时一并处理。
