# 整帧丢失恢复(NACK count = 0)

> 自包含文档。仓库 `E:\code\AnyShare`,分支 `anyshare`;组件 `packages/screen-stream`。

## 1. 问题:整帧全丢没有恢复路径

接收端按帧重组:一帧只要有**至少一个包**到达,就会进入"待重组表(`pending`)",
缺包时按 NACK 请求重传(见 A5 快速重传与 D1 自适应 FEC 文档)。

但如果一帧的**所有包都丢失**(或该帧的包全部在网络层被丢弃),它从未进入待重组表:

- 普通 NACK 扫描看不到它(扫描对象是 pending 里的帧);
- 接收端只能等 **300ms 帧超时**(`FRAME_TIMEOUT`),期间后续帧被按序阻塞;
- 超时后触发关键帧请求(还要再叠加 500ms 去抖),画面会明显停顿/花屏。

自适应 FEC 关闭校验包后,这类事件更可能出现(校验包本来可以零延迟重建单包丢失的小帧)。

## 2. 方案:用 `count = 0` 表示"整帧全部重发"

NACK 报文本来的语义是"这一帧缺这几个包"(位图)。新增一个约定:

```
count = 0  且 payload 为空  =>  请把这一帧的所有数据包重发一遍
```

- **接收端**如何发现:扫描 `next_expected .. max_frame_seen`(高水位)之间
  **既不在 pending、也不在 ready** 的帧号,并且满足"高水位已超前 ≥2 帧"(与快速重传同样的
  判据,避免把乱序误判为缺失)。每次扫描最多报告 2 个这样的帧号。
- **发送端**如何响应:收到 `count = 0` 的 NACK 后,从最近 48 帧的历史缓存里取出该帧的
  全部数据包,逐个重发一次;**绕过**每帧 2 个包的重传预算(那个预算用于防止 NACK 放大,
  不应用来放弃整帧)。同一帧只服务一次,重复请求被忽略。
- **不重发校验包**:历史缓存里只存数据包(校验包随原始帧发送,重传数据包即可)。

## 3. 代码位置
- `packages/screen-stream/src/transport.rs`
  - `Nack::encode`:count==0 时位图为空;
  - `Nack::from_packet`:接受 count==0 且 payload 为空,返回 `missing = []`;
  - `Reassembler::missing_candidates`:新增"空洞帧"扫描,返回 `(frame_id, 0, [])`;
  - 单测:`fully_missing_frame_is_requested_as_a_whole`(帧 2..6 全丢 → 请求 count=0)、
    `whole_frame_nack_roundtrips`。
- `packages/screen-stream/src/sender.rs`
  - `apply_nack`:count==0 → 重发该帧全部数据包、标记预算已用尽;单测
    `whole_frame_nack_resends_every_packet_once`(3 个包全部重发,重复请求返回 0)。

## 6. 已知限制
- 每次扫描最多报告 2 个空洞帧,避免一次请求过大的历史重发;连续空洞会在后续扫描里逐个补齐。
- 只在历史缓存(48 帧 ≈ 1.4 秒 @32fps)内可恢复;更早的帧只能靠关键帧。
- 接收端仍然只对 `next_expected .. max_frame_seen` 之间的空洞发请求;若高水位本身不再前进
  (发送端停止),不会产生请求——此时会话已结束/超时,由既有看门狗处理。
