# 串流清晰度:亮度锐化(发送端)

> 自包含文档。仓库 `E:\code\AnyShare`,分支 `anyshare`;组件 `packages/screen-stream`。

## 1. 问题

屏幕共享的画面要经过四道"软化":

1. **降采样**:源屏 2880×1800(或虚拟屏 1920×1080)按目标高度缩放;
2. **色度抽样**:编码用 4:2:0(YUV420),色度只有亮度的 1/4 分辨率;
3. **量化**:H.264 在 12–14 Mbps 下对高频(文字边缘)必然丢弃细节;
4. **接收端呈现**:窗口与编码分辨率不完全相等时还要再缩放一次。

结果是文字"发虚"、细线条变灰。即使做到 1:1 像素映射,第 1–3 步仍会让笔画边缘变钝。

## 2. 方案:只对亮度做轻度锐化

在**发送端把画面转换成 NV12 之后、交给编码器之前**,对 **Y(亮度)平面**做一次 3×3 非锐化
掩膜(unsharp mask):

```
blur(x,y) = 3×3 均值(边界用最近像素)
Y'(x,y)  = clamp( Y(x,y) + strength × ( Y(x,y) − blur(x,y) ) )
```

- **只处理 Y 平面**:色度不动,避免彩色边缘出现彩边(4:2:0 下色度锐化极易产生彩噪);
- **strength = 35%**:轻度增强,能明显改善笔画对比,又不至于产生白边(振铃);
- 平坦区域 `Y = blur`,输出不变(纯函数性质,有单测锁定);
- 成本:1080p 亮度平面约 2.1M 像素,两遍扫描,实测每帧**约 +1.2ms**(发送端循环从
  13.7ms 到 14.9ms)。

## 3. 开关

- 默认**开启**;
- 环境变量 `ANYSHARE_SHARPEN=0` 关闭(用于 A/B 对照或排查锐化带来的振铃)。

## 4. 代码位置
- `packages/screen-stream/src/convert.rs`
  - `pub fn sharpen_nv12_luma(y: &mut [u8], width: u32, height: u32, strength: u32)`;
  - 单测 `sharpen_boosts_edges_and_leaves_flat_areas_alone`:
    平坦图像不变;孤立亮点变亮;strength=0 与小于 3×3 的图像是 no-op。
- `packages/screen-stream/src/sender.rs`
  - `fn maybe_sharpen(nv12, w, h)`:读取 `ANYSHARE_SHARPEN`,调用上面的函数;
  - GPU 转换路径:`composite_pointer_nv12(...)` 之后立刻锐化(此时指针已合成,锐化会
    连带增强光标边缘,视觉上更清晰);
  - CPU 转换路径:`bgra_to_nv12(...)` 之后锐化(`i420` 缓冲的前 `w*h` 字节即 Y 平面)。

## 6. 实测(虚拟屏 #2 内画圈,16 秒)
```
sender timing: loop_ms=14.8–15.6  (锐化前 13.7;+约 1.2ms)
sender: t=6s fps=32 mbps=20.2 enc_ms=1.0
receiver: decode queue avg=0.1–3.0ms, e2e(运动段)≈100ms, 0 丢包
```
锐化没有改变帧率与丢包行为,代价是发送端每帧约 1.2ms 的 CPU。

## 8. 已知限制
- 锐化只作用于亮度,Y 与 U/V 的边缘会轻微不一致;在 4:2:0 极限下这是可接受的折中。
- 对**极高对比度的斜线**仍可能有轻微白边;如需更强效果应改为编码端 4:4:4(见清晰度路线图)。
- 锐化不改变编码器的量化损失:码率过低时文字仍会被抹平,提高码率/分辨率才是根本手段。
- 锐化强度目前是编译期常量(35%),未暴露为配置项。
