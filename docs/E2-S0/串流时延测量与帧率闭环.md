## 1. 为什么需要"钟差校准"

### 1.1 时延是怎么算出来的
发送端给每个编码帧(`AU`,access unit)打时间戳:该帧**被采集/提交编码**那一刻的墙钟
(Unix epoch,单位 100 纳秒)。接收端拿到这帧后,若直接用"自己的现在"减去"发送端的时间戳",
得到的是:

```
接收端现在 - 发送端时间戳 = 真实时延 + (接收端时钟 - 发送端时钟)
```

两台机器的时钟**没有被同步过**。本项目实测:同一局域网内,Ubuntu 的时钟比 Windows
**快 1.24 秒**。于是日志里曾出现恒定 `e2e ≈ 1150 ms`,而实际时延只有百毫秒级 ——
这是纯测量误差,不是串流问题。

### 1.2 解决办法:UDP 往返探测(类似 NTP 的最简形式)
接收端每秒向发送端发一个 `PING`,发送端立刻回 `PONG`。四个时间戳:

| 记号 | 含义 | 谁的钟 |
|---|---|---|
| t1 | 接收端发出 PING 的时刻 | 接收端 |
| t2 | 发送端收到 PING 的时刻 | 发送端 |
| t3 | 发送端发出 PONG 的时刻 | 发送端 |
| t4 | 接收端收到 PONG 的时刻 | 接收端 |

假设上下行时延对称:

```
offset = ((t2 - t1) + (t3 - t4)) / 2      // 发送端时钟 - 接收端时钟
rtt    = (t4 - t1) - (t3 - t2)            // 往返时延
```

之后每帧的真实时延:

```
e2e = (接收端现在 + offset) - 帧时间戳      // 全部换算到发送端时钟系
```

**符号约定**:`offset` 是"发送端时钟减接收端时钟"。本项目实测 `offset ≈ -1.23 s`
(即接收端快 1.23 秒),与独立用 HTTP 时间戳比对的结果一致。

### 1.3 报文格式(实现约定)
```
PING:  8 字节 magic "ANYSLAT1" + 8 字节 nonce + 8 字节 t1(微秒)   = 24 字节
PONG:  8 字节 magic "ANYSLAT2" + 8 字节 nonce + 8 字节 t1
       + 8 字节 t2 + 8 字节 t3                                    = 40 字节
```
- 时间单位微秒(`u64`),两端口径一致。
- 接收端只接受 **nonce 与 t1 都与自己最近一次 PING 相同**的 PONG(防串包)。
- 发送端的数据 socket 已经 `connect()` 到接收端地址,内核只会把接收端发来的包交给它,
  因此不存在"任何人发 PING 都能让发送端回包"的反射放大风险;接收端也从不向未知源回包。
- 采样策略:保留最近 5 个样本,取 **RTT 最小**的那个(受队列抖动影响最小);
  `RTT > 500ms` 或 `|offset| > 1 天` 视为不合理样本直接丢弃。
- 未完成校准前,**不参与统计**(否则 1.24 秒的假峰值会污染平均值)。

## 2. 接收端解码吞吐与"帧率闭环"

### 2.1 问题
接收端用 ffmpeg 子进程软解 1080p。实测这台 Ubuntu 机器约能解码 25–30 帧/秒;
发送端按 30–60 帧/秒编码时,解码线程来不及消费,帧在**有界队列(容量 4)**里堆积,
极限情况下每帧多等 100–300ms —— 这些等待就是延迟。

**关键区分**:接收端每秒"解码了多少帧"这个数字,既可能是"它只能解这么多",也可能是
"这一秒画面本来就没变化/发送端没发那么多"。只看它无法判断,必须和**发送端自己这一秒
编码了多少帧**比较。

### 2.2 控制律
接收端每秒通过 `/screen/bitrate` 上报 `frames`(该窗口解码帧数);发送端在同一状态里
已有自己的 `lastStats.frames`(该窗口编码帧数)。令:

```
encoded = 发送端本窗口编码帧数
decoded = 接收端本窗口解码帧数
```

- 若 `decoded + 3 < encoded`:接收端明显跟不上 → 目标帧率下调到 `decoded + 2`,
  但**一次最多降 2 fps**(避免某一秒静止画面把目标直接打到 10 fps 之后爬不回来);
- 否则若 `lossRate < 0.5%` 且 `encoded >= 目标 - 1`(说明编码器已经贴着目标跑)
  且目标 < 60 → 目标 +2(探测更高帧率是否可行);
- 目标夹紧在 **10–60 fps**,只有变化时才下发(`RsScreenSender::set_max_fps`)。

### 2.3 VFR 限速为什么要改成"截止时间累加"
发送端有"可变帧率门(`VfrGate`)":内容没变化就不编码;另外有帧率上限。
旧实现是"距上次编码 >= 1/目标 才允许":

- 采集以 60Hz 提供画面,目标 25fps(间隔 40ms);
- 帧每 16.7ms 到一次:0(编码)、16.7(跳过)、33.3(跳过)、50(编码)… → 实际 20fps;
- 即 60/k 量化:25 永远到不了,只能到 20 或 30,闭环在 20 附近打转。

改为累计"下一次允许编码的时刻"(`next_allowed += interval`),并允许最多 4 倍间隔的追帧
上限(避免长时间停滞后突发):

- 0(编码,下次 40)、50(编码,下次 80)、83.3(编码)、133.3(编码)… 平均 25fps ✓

## 3. 顺带的性能修复:NV12→ARGB 转换
接收端把 ffmpeg 输出的 NV12(每像素 1.5 字节)转成窗口用的 ARGB。旧实现逐像素做
`宽度×行` 乘法并对每个像素重新读一次 UV。新实现:

- 行内切片(消除每像素乘法与边界检查的重复计算);
- 4:2:0 色度由 2×2 像素共享,一次 UV 读取服务**相邻两个像素**;
- 奇数宽兜底使用与旧实现相同的色度对(`col/2`),保证内存布局等价。

颜色矩阵保持 BT.601 limited(与发送端编码器一致),并有单测锁定已知值:
Y=16→黑、Y=235→白、中性色度→灰(R=G=B)。

## 7. 已知限制
- 单向时延不对称时(上行拥塞),`offset` 会有 0.5×(不对称量) 的偏差;取最小 RTT 样本可
  减轻但不能完全消除。需要绝对精度时应改用硬件时间戳或 PTP。
- 帧率闭环以 1 秒为周期,收敛需数秒;它只限制"编码帧率上限",不改变内容驱动的 VFR
  (静止时仍然不编码)。
- 奇数宽度的 NV12 只是防御性分支:实际编码器输出总是偶数宽高,1080p/1280p 走偶数路径。
