**结论(③)**:
1. 注入链路五端可行的 Android 部分落实:点击/滚动/文本注入 + 毫秒级延迟,真机 ColorOS 16 通过。
2. 文本输入走 `ACTION_SET_TEXT` 可行;受控端真实键盘事件仍不可做(维持评估文档 §2.1 结论)。
3. 光标为**自绘叠加层**(非系统指针),确认"体验降级"定位;hover 无法合成(维持文档结论)。
4. **真实设备上的授权是硬门槛**:无障碍开关 + 叠加层权限都必须走用户 UI(ColorOS 连 shell 都拒授 appops)——产品上须内置引导页(NF-S5 用途说明文案的落点)。
5. **实现坑(记入方案)**:Android 8+ 清单 receiver 收不到**隐式**广播(实测静默丢弃),测试驱动须用**显式组件广播**;产品方案不受影响(走网络通道)。
6. 保活基线 OK,但 ColorOS 深度省电(如「省电模式/超级省电」)与长时冻结未测,列入真机深度测试项。

**待补(③)**:
- 超级省电/长时(>1h)冻结场景
- 多指组合、长按拖动、手势进行中连续注入的拒绝行为
- 叠加层 inset 补偿(`setFitInsetsTypes(0)`)后在真机复测坐标一致性

## ① Wayland libei — 实测结果(2026-10-16,Ubuntu 24.04.4 / GNOME 46 / Wayland)

> 注:用户环境实为 Ubuntu **24.04.4**(非 22.04)。这落在评估文档最关心的"存量 LTS 灰区"里,结论比预期乐观。

**环境**:GNOME Shell 46.0,mutter Wayland 会话(`loginctl Type=wayland`),libei1 1.2.1,libeis1 1.2.1,xdg-desktop-portal 1.18.4-1ubuntu2.24.04.2,xdg-desktop-portal-gnome 46.2。X11 兜底会话(`ubuntu-xorg.desktop`)存在。

**接口版本**:RemoteDesktop v2 / InputCapture v1 / ScreenCast v5。

| 实验 | 方法 | 结果 |
|---|---|---|
| 注入通道(RemoteDesktop) | CreateSession → SelectDevices(键盘+鼠标) → Start → ConnectToEIS | ✅ 全链路通过;**ConnectToEIS 取得 EIS fd**(libei 注入握手成功) |
| 注入授权 UX | Start 时系统弹「远程交互」授权框 | ✅ 每会话需用户点击「允许」(未观察到"记住"选项);SSH 场景下用户须在桌面前 |
| 捕获通道(InputCapture) | CreateSession → GetZones → ConnectToEIS → SetPointerBarriers → Enable | ✅ 会话/区域(**真实屏幕 2048x1280**)/EIS fd/Enable 全部通过 |
| 指针屏障 | SetPointerBarriers 传 4 条边(0/内缩 1px 两版) | 🟡 调用被接受(response=0)但 `failed_barriers` 报全部失败——mutter 46 的 barrier 语义细节留 S1 落实(不影响捕获通道成立) |
| InputCapture 授权 UX | CreateSession/Enable 流程 | ✅ 未弹窗(与 RemoteDesktop 不同) |

**工程要点(实测踩坑,直接进 S1 设计)**:
1. **Request 必须订阅先行**:portal 的 Response 信号可能在方法返回前到达,先调用后订阅会产生随机超时(本次调试的主坑);正确姿势 = 预计算 `request/<sender>/<handle_token>` 路径先订阅。
2. 签名细节:InputCapture.CreateSession 是 `(sa{sv})`;SetPointerBarriers 是 `(o a{sv} aa{sv} u)`;Enable/Disable/Release 为**无返回值**方法。
3. SSH 调试可行(设 `DBUS_SESSION_BUS_ADDRESS=/run/user/<uid>/bus`),配合 `notify-send` 类通知提醒用户点授权框效果良好。
4. 疑点(待 S1):客户端异常退出且未走 Disable/Release 时,偶发后续会话异常;产品实现必须有可靠的会话生命周期管理。

**结论(①)**:
- 评估文档 §2.1 的 Wayland 灰区在 **Ubuntu 24.04 + GNOME 46 上均为绿灯**:普通应用(经 portal)可同时拿到**注入 EIS 通道**与**捕获 EIS 通道**。libei 1.2.1 已满足 EIS 握手;生态工具(Deskflow)要求的 libei 1.3+/GNOME 48+ 是针对其具体实现,不构成平台能力上限——自研实现(或引入 libei 客户端库)可按 1.2 API 先行。
- 授权模型明确:注入需**每会话**用户确认;GNOME 46 的 InputCapture 无弹窗(捕获路径更顺)。
- 兼容矩阵更新建议:Ubuntu 24.04+/GNOME 46+ = Wayland 可用;更老发行版(Ubuntu 22.04/GNOME 42)仍建议 X11 会话兜底(未实测,理论无 libei portal)。

**产物**:`linux-kit/probe.py`(订阅先行版探测脚本,可复跑;`SKIP_RD=1` 跳过需点击的注入段)、`linux-kit/check.sh`(只读环境检查)。

### 模式 B(VDD 虚拟扩展屏)演示(2026-10-16/17 凌晨)

**已打通的最小闭环**:`VDD 虚拟显示器 → DXGI Desktop Duplication 抓帧 → libx264 → MPEG-TS/UDP → Ubuntu ffplay 显示`

| 项 | 结果 |
|---|---|
| VDD 安装 | winget 装 VDD Control(25.7.23),驱动经 GUI 安装,Windows 多出"Generic Monitor (VDD by MTT)",默认 800x600@30(可配 800x600~3840x2160 等多档;实测已调至 1920x1080@60) |
| 抓帧 | `ffmpeg ddagrab=output_idx=2`(虚拟屏为本机第 3 个输出);本机 GPU=AMD Radeon 780M |
| 端到端延迟(调优后) | **M-V ≈ 37ms,1080p60,丢帧 0.5%,180s 稳定** —— 达到"可交互拖动窗口"水平 |
| 结论 | **模式 B 技术路线全部验证通过,零自研驱动、零签名依赖**(VDD 为 MIT 且已 Microsoft 签名) |

**延迟调优关键(1080p60 配置,全部已验证)**:
- 发送端:`-muxdelay 0 -muxpreload 0`(去 MPEG-TS 封装缓冲)+ **`-flush_packets 1`(关键!UDP 输出立即冲刷,0.8s→37ms 的绝大部分来自这里)** + `-tune zerolatency -g 60`
- 播放端:`-fflags nobuffer -flags low_delay -framedrop -probesize 32 -analyzeduration 0`(x264 流用极小探测量;**注意:AMF 流的参数集(SPS/PPS)依赖更多探测数据,该组合会在本机 FFmpeg 构建上报 "non-existing PPS"/无法打开——h264_amf+mpegts 输出连文件都解不开,属该构建缺陷,已记录,产品用硬件编码需另选容器或无容器传输验证**)
- 结论性经验:低延迟串流里 **flush_packets > 一切封装参数**;AMF 硬件编码路径需独立验证(S1 事项)

**本次踩坑与修复(重要,写进安装引导)**:
1. **Hyper-V 虚拟交换机不可绑无线网卡**:本机 Hyper-V 外部交换机(realNet)绑在 WLAN 上,导致 Windows 侧 TCP 发送被掐至 50KB/s、UDP 高丢包、ping 抖动(20→100ms),而 Ubuntu→Windows 方向正常(非对称故障)。诊断路径:延迟正常+吞吐崩塌→MTU/丢包排除→`ss -tin` 看 TCP 内部(无重传/窗口正常)→UDP 裸测对比(31MB/s 发送 vs TCP 50KB/s)→路由表锁定 vEthernet 虚拟适配器。
2. **修复**:Windows 与 Ubuntu 全部改有线连接 + 关闭无线桥接的虚拟交换机 → scp 从 0.05MB/s 恢复至 **9.2MB/s**(同网段直连目标 ~100MB/s,剩余为实测环境上限)。
3. **产品启示**:Windows 端如果有 Hyper-V/VM 环境的用户,虚拟交换机绑无线是隐蔽的流量杀手;AnyShare 网络自检/诊断功能值得把"虚拟适配器路径检测"列入(错误提示可精确到"检测到流量经过绑无线网卡的 Hyper-V 虚拟交换机")。
4. VDD 官方警告同样记入安装引导:大版本显卡驱动更新前须先卸载 VDD,否则可能开机黑屏。

**演示操作步骤(可复跑)**:
- Windows:`ffmpeg -filter_complex "ddagrab=output_idx=<虚拟屏idx>,hwdownload,format=bgra,fps=30" -c:v libx264 -preset ultrafast -tune zerolatency -b:v 2500k -maxrate 3000k -bufsize 1000k -pix_fmt yuv420p -g 30 -f mpegts "udp://<ubuntu-ip>:53319?pkt_size=1316"`
- Ubuntu:`ffplay -fflags nobuffer -flags low_delay -framedrop "udp://0.0.0.0:53319?overrun_nonfatal=1"`(需 `DISPLAY=:0` + Xwayland XAUTHORITY;ufw 需放行 53319/udp)
- 虚拟屏识别:PowerShell `[System.Windows.Forms.Screen]::AllScreens` 对照分辨率;ddagrab 的 output_idx 与 DISPLAYn 编号不同,用"抓单帧看分辨率"法确认
