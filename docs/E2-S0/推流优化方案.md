# E-2 模式 B(虚拟扩展屏)推流优化方案

> 2026-10-17。背景:S1 演示链路(VDD 抓帧 → libx264 → MPEG-TS/UDP → ffplay)在 1080p60 下已达到相对时钟偏差 ~1ms、丢帧 0.5%,但**用户体感与 Windows 远程桌面(RDP)有明显差距**;要求:找成熟、跨端(ARM 手机/电脑、Win、Linux 各发行版、macOS)的开源方案,硬件加速严格按"独显 > 核显 > CPU"链,支持增量传输与参数/色深优化。

## 1. 为什么比不上 RDP(先正名)

RDP 的"顺滑"不是魔法,是三个我们目前没有的东西:
1. **变更跟踪(change tracking)**:RDP 只编码"变化区域"(脏矩形),静态画面 0 码流 0 延迟;我们目前是**无条件全帧 60fps 编码**(ddagrab 只看得到完整帧)。
2. **编码器内建低延迟模式 + 硬件路径全程**:RDP 在局域网用 AVC444 硬件编码,编码管线延迟在个位毫秒级;我们当前是 CPU 软编(780M 核显的 AMF 路径在本地 FFmpeg 构建里是坏的)。
3. **接收端由系统合成器直接呈现**:接近零拷贝、无 ffplay 的尽力而为渲染。

结论:**要贴 RDP,核心是①增量/按需编码 + ②全硬件链路 + ③专业传输层**,而不是继续抠容器参数。

## 2. 成熟开源方案选型对比

| 方案 | 跨端覆盖 | 硬件加速 | 增量传输 | 延迟水平 | 许可 | 结论 |
|---|---|---|---|---|---|---|
| **GStreamer(媒体层)+ WebRTC(传输层)** | ★★★★★ Win/Linux/Android/ARM/macOS 全支持;HarmonyOS 可接 MediaCodec | ★★★★★ 元素自动排行:nvcodec/vaapi/qsv/vt/mediacodec/d3d11 | 采集元素支持脏区(平台相关) | 30–80ms 可达 | LGPL(可动态链接商用量产) | **主推荐** |
| FFmpeg(媒体层)+ 自研 UDP+FEC(传输) | ★★★★★ | ★★★★ 编码器齐全,容器/传输全自研 | 需自研 | 30–100ms | LGPL | 备选(我们已在用 FFmpeg,但传输层自研成本高) |
| Moonlight/Sunshine 架构 | ★★★★ 借鉴对象 | ★★★★★ | ✓(NVFBC/DDAPI 脏区) | 10–20ms(游戏级) | **GPL — 只能读思路不能抄代码** | 作为架构参照 |
| VNC/RFB 系(TigerVNC 等) | ★★★★★ | 弱 | ✓(脏矩形是其核心) | 静态好、动态差 | GPL/部分 BSD | 不作为视频链路,可参考脏矩形编码思路 |
| RDP 协议 | — | — | ✓ | 快 | 非开源,协议未开放 | 只能当对标基准 |

**推荐组合:采集/编码/解码 = GStreamer;传输 = WebRTC(或 GStreamer 的 webrtcbin)**。
理由:一份 API 覆盖全部目标平台;硬件元素自动择优;WebRTC 自带 NACK/PLI/FEC/拥塞控制/自适应码率(这些自研要几个月);浏览器可作为天然接收端(承接"浏览器接收"能力)。

## 3. 硬件加速选型链(独显 > 核显 > CPU)

统一探测逻辑:枚举系统可用编码器 → 按固定优先级探测"可用且实测出帧" → 否则降级。建议实现为启动时自检(编码 1 秒测试帧,成功才选用),避免同平台驱动差异踩坑。

| 平台 | 独显优先 | 核显 | CPU 兜底 |
|---|---|---|---|
| Windows | NVENC(NVIDIA)/AMF(AMD) | QSV(Intel)/D3D12VA | libx264/libx265 |
| Linux x86 | NVENC | VAAPI(Intel iHD / AMD Mesa) | libx264 |
| Linux ARM(RPi/RK/国产) | — | V4L2M2M(RPi)/Rockchip MPP/VAAPI | libx264 |
| macOS(含 M 系) | — | VideoToolbox(统一) | libx264 |
| Android/ARM 手机 | — | MediaCodec(H.264/HEVC/AV1) | libx264(不推荐,耗电) |
| 鸿蒙 NEXT | — | MediaCodec 等价能力(ArkTS 侧) | 同左 |

GStreamer 侧就是一个 `encodebin`/`autovideosink` 加 rank 配置的问题;FFmpeg 侧需自行按表实现探测链。

## 4. 用户四问的直答

**Q1 只传更改的部分?** ——能,但要分层理解:
- **今天可拿到的信息**:Windows 的 DXGI Desktop Duplication(桌面复制的底层 API)**本身就返回脏矩形**(`DirtyRects`);我们目前用的 ffmpeg 封装(ddagrab)把它丢了。自研采集层(Rust `windows` crate 调 DXGI,或 GStreamer 对应 src)可以拿到。
- **为什么不能直接把"H.264 只编码脏区"当主力**:H.264 是逐帧差分编码,帧间依赖+P 帧本身就"只编码变化",**部分刷新的价值主要体现在"没有变化时完全不编码"(VFR/按需帧)**,而不是每帧只编一小块。工业界做法:脏区 → 决定是否发帧(静态 0 码流);进阶(多窗口/大屏)才做分块多流。
- **落地顺序**:P1 做"脏区→按需编码(静止时 0 流量、鼠标一动才编码)",这一步就能让静态桌面延迟趋近于 0、CPU 占用趋近 0;P2 再评估分块。

**Q2 降低色深?** ——不推荐作为主手段,收益计算不划算:
- 我们的链路已是 4:2:0 8bit(色度已减半),再降(比如 16bit 色)会先在文本边缘和渐变上翻车;
- 且**带宽大头在编码器效率,不在色深位数**(H.264→HEVC 省约 40%,HEVC→AV1 再省约 20%,这些是硬件支持的,免费拿);
- 注意一个已有坑:部分路径输出 `yuvj420p`(JPEG 全范围色彩),监视器和播放器之间会有对比度/色彩偏差,统一改为 `yuv420p`(limited range)是**零成本画质修正**;
- 要省带宽的正确顺序:**静止不编码(VFR)→ HEVC 硬编 → 动态调码率/帧率/分辨率(WebRTC 拥塞控制自动做)→ 色深才是最后考虑**。

**Q3 卡顿怎么来的?** 当前链路的四个抖动源:
1. **CPU 软编**:x264 ultrafast 1080p60 在核显机上帧时间有抖动,是丢帧主因(180s 丢 80 帧即 0.7%);
2. **无传输层保护**:裸 UDP 无 FEC 无重传,任何链路瞬时丢包都直接造成画面跳变;
3. **接收端软解 + ffplay 尽力渲染**:无 VSync 感知、时序粗糙;
4. **无节奏控制**:发送端不管链路状况匀速发送。

**Q4 优化方案(总)**:

| 阶段 | 动作 | 预期收益 |
|---|---|---|
| P0(1–2 天,不动架构) | 接收端改硬件解码(VAAPI/平台解码);`-flush_packets 1` 已在;统一 yuv420p;真延迟测量(高速摄影/带时间戳测试图) | 抖动明显下降,拿到真实延迟数字(当前 M-V 只是流内偏差,不能代表端到端) |
| P1(1–2 周) | 自研采集:DXGI 脏区 → 按需编码(VFR);硬件编码探测链(AMF 走独立验证,或暂时 x264+多切片);传输换 RTP+FEC(轻量)或直接上 WebRTC | 静态 0 延迟 0 码流;动态延迟逼近 30–50ms;丢包不再抖动 |
| P2(3–6 周) | WebRTC 全量(拥塞控制、自适应码率、PLI/NACK);接收端 Flutter 平台解码器 + 纹理呈现(或 media_kit/mpv 方案);HEVC 硬编;多显示器;窗口级采集(拖哪个窗口传哪个) | 达 RDP 同级体验区间(局域网 30ms 内),跨端矩阵完整 |
| P3(可选) | HDR、444 文本增强模式、分块增量、AV1 | 特殊场景 |

**跨端接收端建议**:Flutter 侧优先评估 `media_kit`(封装 libmpv,LGPL):一份代码在 Win/Linux/macOS/Android 全端播 RTP/WebRTC 流且自带硬件解码与低延迟参数;**备选**:自研 Flutter 纹理 + 各平台解码器 FFI(工作量中等但完全可控)。鸿蒙走 MediaCodec 等价封装。

## 5. 真延迟测量方法(产品验收用)

M-V 指标只是流内相对值。正式标准用两种:
1. **时间戳叠加法**:发送端在角落渲染毫秒级时钟,接收端截图/拍照对比两侧时钟,差值为玻璃到玻璃延迟;
2. **标记注入法**:程序每 N 秒注入白/黑闪帧,接收端光电或摄像头测量(可自动化,用于 CI/回归)。

验收目标(局域网有线):**静态画面 0 码流**;动态 1080p60 **玻璃到玻璃 ≤ 50ms**;**丢包 1% 场景无可见跳变**(FEC 生效)。

## 6. 风险与注意事项

- WebRTC 在 Rust 侧(`str0m`/`webrtc-rs`)成熟度需 S1 评估;GStreamer 的 webrtcbin 更稳但引入 GStreamer 运行时依赖(打包体积 + 授权审查 LGPL 动态链接即可)。
- Sunshine 系为 GPL:**只准读架构,不准抄代码**(协议设计、FEC 方案、编码参数思路可学习)。
- 手机端采集需要系统权限(Android 投屏权限、iOS 录制权限、鸿蒙长时任务),与本地编码功耗预算一起在 S1 评估。
- "比 RDP 更顺"不能作为目标(RDP 是本地合成+系统级优化);合理目标是"同体验区间内的跨平台开源实现"。
