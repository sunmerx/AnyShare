## 1. 结论速览

| | Windows | macOS | Linux | Android | 鸿蒙 NEXT |
|---|---|---|---|---|---|
| **边缘穿越·受控端**(被一套键鼠控制) | ✅ 成熟 | ✅ 可行(需辅助功能权限) | ✅ X11 成熟 / 🟡 Wayland 需新版桌面环境 | 🟡 受限可行(无障碍注入,体验降级) | ❌ 不可行(注入 API 为系统级权限) |
| **边缘穿越·控制端**(键鼠来源) | ✅ 成熟 | ✅ 可行(同权限) | ✅ X11 / 🟡 Wayland | ✅ 可行(触屏当触摸板,KDE Connect 已验证) | ✅ 可行(纯网络发送,无特殊权限) |
| **扩展屏·副屏显示端**(接收视频流 + 触摸回传) | ✅ 可行 | ✅ 可行 | ✅ 可行 | ✅ 可行 | ✅ 可行 |
| **扩展屏·主控端**(提供"虚拟显示器") | ❌ 硬阻塞(驱动签名) | 🟡 半私有 API | 🟡 视会话类型 | — | — |

**总判断:**

1. **边缘穿越模式可行,推荐作为 E-2 的落地形态**,但五端能力不等齐:桌面三端(Win/mac/Linux)可做全功能对等;Android 建议首期只做**控制端**(手机当触摸板/键盘);鸿蒙 NEXT 只能做控制端,**永远做不了受控端**——这是系统权限层面的硬限制,不是工程量问题。
2. **扩展屏模式的瓶颈在主控端而非副屏端**:把副屏暴露为操作系统的"第 N 块显示器"在 Windows 上需要 IddCx 间接显示驱动 + 微软签名(与本项目"无代码签名自分发"的裁决直接冲突),macOS 依赖半私有 API。**真·虚拟显示器不建议做**;可行的降级形态是"窗口投放 / 应用内远程画布"(见 §3.3),但视频管线本身工程量大,建议单独立项或无限期推迟。
3. **传输、发现、安全全部复用现有基础设施**(TLS + 指纹配对、归属者模型、Rust core),E-2 的净增量集中在:一条低延迟长连接通道 + 各端输入注入/捕获模块 + 配对几何配置 UI。

## 2. 模式一:边缘穿越(类 Barrier / Synergy / Logitech Flow)

各设备显示各自内容,键鼠按屏幕空间位置关系跨设备流转。核心 = **受控端输入注入** + **控制端输入捕获** + **切换逻辑**。

### 2.1 受控端输入注入(核心风险点,逐平台)

| 平台 | 技术路径 | 结论 | 限制与摩擦 |
|---|---|---|---|
| Windows | `SendInput`(绝对/相对鼠标 + 全键盘) | ✅ 成熟。Barrier、Mouse without Borders 均此路径 | **提权窗口(UAC 提示框、以管理员运行的程序)不受注入输入**,UAC 安全桌面永远不可控;缓解:检测到焦点在提权窗口时挂起并提示,或引导以管理员运行 |
| macOS | `CGEventPost`(HID 会话级) | ✅ 可行,Barrier 同路径 | 需用户在「系统设置 → 隐私与安全性 → 辅助功能」手动勾选授权(一次性);系统开启 Secure Input(密码框)期间受限。本项目本就无签名无公证分发(见需求文档 §4.5),授权摩擦属于同类既有成本,不新增裁决项 |
| Linux X11 | `XTest` 扩展 | ✅ 成熟 | 无明显限制 |
| Linux Wayland | `libei`(输入模拟接口)+ xdg-desktop-portal `InputCapture`/`RemoteDesktop` | 🟡 方向已定但生态尚新 | Deskflow 已用 libei 1.3+ 实现注入;但合成器支持要求较新版本(GNOME 48+ / KDE Plasma 6.x+),合成器既不支持 libei 也不支持 wlr-virtual-pointer 时无解。**Ubuntu 24.04 LTS 这类存量用户需要等新版或切 X11 会话**。需求文档兼容性基线(Ubuntu 20.04+/Debian 11+/Fedora 36+)中相当比例的发行版组合落在灰区 |
| Android | `AccessibilityService.dispatchGesture`(API 24+)| 🟡 受限可行 | 能合成:点按、长按、滑动、双指滚动(视觉光标用 `SYSTEM_ALERT_WINDOW` 悬浮窗自绘)。**做不到**:真实鼠标光标、hover 悬停、向任意应用全局注入键盘按键。文本输入只能依赖焦点节点的 `ACTION_SET_TEXT` 或"写剪贴板 + 粘贴手势",自绘 UI/游戏不可控。分发走 APK 侧载,无 Google Play 对无障碍 API 的政策风险,但需引导用户手动开启无障碍开关(NF-S5 要求给用途说明) |
| 鸿蒙 NEXT | `injectInputEvent` 等 | ❌ **不可行** | 注入接口为**系统级权限**,普通三方应用不可获取(华为生态只有系统应用/华为自家"超级终端"具备该能力)。无绕行路径(侧载也不行)。**永久结论:鸿蒙 NEXT 不做受控端** |

### 2.2 控制端输入捕获(键鼠来源)

| 平台 | 技术路径 | 结论 |
|---|---|---|
| Windows | 低级鼠标钩子(`WH_MOUSE_LL`)/ Raw Input,边缘处拦截并吞掉事件 | ✅ 成熟 |
| macOS | `CGEventTap`(与注入同用辅助功能权限) | ✅ 可行 |
| Linux X11 | `XGrabPointer` / 指针约束 | ✅ 成熟 |
| Linux Wayland | portal `InputCapture`(Barrier 式边缘屏障的官方标准路径) | 🟡 同 §2.1,依赖新版 GNOME/KDE,已有实现(InputLeap)存在会话恢复等边角 bug |
| Android | 触屏手势 → 相对坐标增量;软键盘 → 文本事件 | ✅ 简单,KDE Connect"手机当触摸板"已长期验证 |
| 鸿蒙 NEXT | 同 Android,纯网络发送 | ✅ 简单 |

### 2.3 切换逻辑与体验细节(产品层,中等工作量,无平台风险)

- 屏幕几何配置 UI(拖拽摆放各设备屏幕,类似 Barrier 的 Screens 界面),需处理各端 **DPI 缩放**差异导致的坐标映射。
- 触发方式:边缘穿越(可设灵敏度/粘滞角)+ 热键切换(Ctrl+Alt+1/2…)兜底。
- 跨设备状态同步:修饰键按下状态(按住 Shift 穿越边缘)、按键重复、NumLock/CapsLock、**各端输入法状态独立**(不强制同步,文档说明即可)。
- 多显示器控制端:按每块显示器的实际几何参与排布。
- 会话管理:唯一主控仲裁(两台设备同时当主控时的冲突)、断线即停、休眠唤醒重连、空闲自动断开。
- 附带能力(Barrier 不做、AnyShare 可以做加分项):**跨设备拖文件 = 直接触发一次 AnyShare 文件传输**(把 E-2 与主营业务打通,这是相对 Barrier 的差异化卖点);文本剪贴板同步(F-XFER-12 复用)。

### 2.4 边缘穿越小结

| 项 | 评估 |
|---|---|
| 技术可行性 | ✅ 全路径存在,无未知领域;桌面三端有 20 年先例(Barrier/Synergy 系) |
| 主要风险 | Linux Wayland 的发行版碎片化;Android 受控端体验天然降级;杀毒软件对全局钩子/注入的误报(与需求文档风险 R3 同源) |
| 架构契合 | 高(见 §4.3) |

## 3. 模式二:扩展屏(其他设备屏幕作为主设备的扩展屏)

### 3.1 阻塞点:主控端虚拟显示器

"副屏"要成为操作系统眼里的真实显示器,主控端必须创建虚拟显示输出:

| 平台 | 路径 | 结论 |
|---|---|---|
| Windows | IddCx 间接显示驱动(UMDF) | ❌ **硬阻塞**:驱动须微软 attestation 签名(EV 代码签名证书 + 硬件开发者中心账号),与需求文档 §4.5"无代码签名、GitHub 自分发"的裁决直接冲突。竞品 spacedesk/Duet 都是靠已签名驱动实现的,这条路我们当前走不通 |
| macOS | `CGVirtualDisplay` | 🟡 半私有 API,无签名自分发或许可用,但无文档保证、系统大版本升级易碎,不可作为产品承诺 |
| Linux | X11 可用虚拟输出;Wayland 三方应用无标准路径 | 🟡 可作技术演示,不可承诺 |

### 3.2 视频管线(无论何种形态都要付出的成本)

- **编码器选型受 Apache-2.0 约束**:x264 是 GPL 不可用。现实选项:openh264(BSD,注意 AVC 专利池条款)、libvpx(VP8/VP9,免专利税,更稳)、或各平台硬件编码器(MediaFoundation / VideoToolbox / VAAPI,工程量再 +)。
- **延迟**:LAN + 低延迟调参(无 B 帧、zerolatency),1080p60 约 4–8 Mbps,端到端 40–80ms 可达成——够"文档/网页/聊天"副屏,**不够游戏和视频剪辑**。
- 副屏端解码渲染(Android/鸿蒙硬解 + Flutter Texture,桌面端软解即可)无风险。

### 3.3 可行降级形态(若一定要做)

- **形态 A:窗口投放 / 远程画布(推荐)**——不做系统级虚拟显示器:主控端 AnyShare 内一块"画布窗口",把指定应用窗口(Windows.Graphics.Capture / macOS ScreenCaptureKit 均支持单窗口捕获)或画布内容编码后流到副屏设备;副屏上的触摸/鼠标/键盘回传,由主控端的画布窗口**自行消费**(窗口有焦点,无需 OS 级注入)。零驱动、零签名问题,体验是"把一个窗口丢到平板上看并操作",覆盖了该模式 80% 的实际诉求。
- **形态 B:HDMI 虚拟插头(仅提及)**——用户花几美元买 dummy plug 骗出真扩展屏,AnyShare 只负责捕获+流+回传。零开发量但依赖外购硬件,不建议作为产品路径,可作为社区 workaround 记录。

### 3.4 扩展屏小结

副屏端(显示+触摸回传)五端全部可行;**卡死在主控端虚拟显示器**。真扩展屏不建议做;若做,只做形态 A,且视频管线 + 捕获 + 回传 ≈ 3 个月量级,建议**单独立项,不与 E-2 边缘穿越绑定**。

## 4. 公共子系统

### 4.1 传输通道

- 复用现有 Rust core:TLS + 双向证书校验 + 指纹配对全部现成,只需**新增一条长连接通道**(TCP 或 WebSocket,挂进现有 server),承载输入事件流。
- 带宽与延迟要求极低:鼠标事件合并上报(coalesce)至 ~125 Hz,仅 KB/s 量级;LAN 有线 RTT <2ms、Wi-Fi 3–10ms,键鼠"手感"达标(Barrier 在 Wi-Fi 上可用是多年公认)。
- 事件协议建议自研精简二进制(参考 Synergy 协议结构但不兼容它),版本字段照常。

### 4.2 安全模型(键鼠注入是高危能力,须比文件传输更严)

1. 默认关闭,**逐设备显式开启** + 仅同归属者(与 PRD 3.3a 的联动要求一致)。
2. 受控期间**屏幕边缘指示条**(参照各 KVM 软件的"被控制"高亮)+ 固定热键一键断开。
3. TLS 双向校验沿用;空闲超时与断线自动终止会话;开启时发系统通知。

### 4.3 与现有架构的契合

- **输入注入放 Rust core**:enigo(MIT/Apache-2.0 双许可)稳定覆盖 Windows/macOS/X11;其 Wayland/libei 后端存在但为实验性(feature flag 后面,有已知 bug)——正好匹配 §2.1 的灰区结论。捕获端可用 rdev(MIT/Apache)或平台原生 API。
- Android 受控端的 AccessibilityService、鸿蒙控制端走平台通道(Kotlin/ArkTS 插件),与现有"平台适配层插件化"原则一致;Android 无障碍部分无法进 Rust,天然分层清晰。
- 与 isolate 架构无冲突:输入通道独立于文件传输的 isolate 拓扑,建议独立常驻连接。

### 4.4 许可与合规

- **Barrier / InputLeap / Deskflow 均为 GPL,只能读思路,一行代码不能搬**(与本项目 Apache-2.0 冲突)。Microsoft PowerToys 的 Mouse without Borders 为 MIT,可参考其 Windows 实现;scrcpy(Apache-2.0)可参考交互设计,但其注入依赖 ADB shell,普通分发不可复用。
- 编码器:若做视频,VP8/VP9(libvpx)无专利负担最稳;openh264 需知悉 AVC 专利池条款(小规模自分发通常无实际风险,记录在案)。
- Android 无障碍权限属敏感权限,NF-S5 的"用途说明"必须落实(侧载分发无商店审核问题)。
- 全局钩子/注入可能触发杀软启发式误报——并入需求文档 R3(SmartScreen/杀软)一并缓解。

## 9. 补充评估(2026-10-16,用户提出):Windows 侧"虚拟扩展屏"路线

> 用户设想:让 Windows 把 AnyShare 共享的远端屏幕**模拟成系统扩展屏**(类投屏),则屏幕布局用 Windows 自带的显示设置即可,**无需自绘布局 UI**,且"光标到边缘卡住/消失"的问题不复存在。要求评估可行性。

### 9.1 问题分解

1. 纯软件边缘穿越下"光标到边缘"的体验问题**可解**:捕获端使用低级鼠标钩子(WH_MOUSE_LL),在边缘处吞掉事件 + 隐藏本机光标 + 将本机光标 warp 回中性位置,远端注入真光标——Barrier / Mouse without Borders 的成熟做法。残留毛刺:全屏独占应用、提权窗口、个别光标绘制异常的应用。**结论:该问题不构成路线否决。**
2. "把远端当系统扩展屏"的本质 = **主控端必须存在一块真实的系统显示器**(虚拟或物理),否则 Windows 无法把窗口渲染到不存在的屏幕上,也不能借显示设置管理布局。

### 9.2 让 Windows 出现"虚拟显示器"的四条路径

| 路径 | 自研驱动+微软签名 | 依赖已签名第三方驱动(VDD) | 硬件虚拟插头(HDMI/DP dummy) | Miracast 投屏协议 |
|---|---|---|---|---|
| 原理 | 自写 IddCx 驱动 | 安装 MIT 开源且已签名的 VDD,Windows 获得真显示器 | 物理小件让显卡认为接了显示器 | Windows 作 Miracast source,远端须实现 sink |
| 签名/成本 | **需 EV 证书+attestation(与"无签名自分发"裁决冲突)**;驱动开发数月 | 不需要自己签名;本机装第三方驱动 | 用户花几美元 | — |
| 可行性 | 高但代价不可接受 | **✅ 高**且零开发 | ✅ 高 | ❌ 否决:Linux 无可用 Miracast sink 实现,Wi-Fi Direct 依赖重,工程量失控 |
| 风险 | rebase/维护、蓝屏责任 | 第三方驱动供应链;VDD 已知"大版本显卡驱动更新需先卸载否则可能黑屏",须引导用户 | 需插拔硬件 | — |

**关键验证点(VDD 路线)**:显示器有了,画面从哪来?→ **不需要驱动提供帧**。DXGI Desktop Duplication(桌面复制)可按显示器抓帧,对间接显示同样有效——VDD 官方定位即为 "Works with OBS, Sunshine, and/or any desktop sharing software",该组合(OBS 采 VDD 屏、Sunshine 串流)是社区验证过的成熟用法。输入回注用 Windows SendInput(与边缘穿越同一套)。**整体链路:VDD 造屏 → 桌面复制抓帧 → 编码串流 → 远端全屏显示 → 远端输入回注 SendInput。**

### 9.3 两条路线的定位差异(重要:不是二选一)

| | 边缘穿越(路线 A) | 虚拟扩展屏(路线 B,本节) |
|---|---|---|
| 用户得到的 | 一套键鼠控多台**各自独立**的电脑 | 把远端变成 Windows 的**第二块屏**(画面是 Windows 内容的串流) |
| 远端状态 | 保留自己的桌面与应用 | 变成"哑屏"(展示 Windows 画面) |
| 光标问题 | 需钩子+隐藏+warp(有边角毛刺) | **无此问题**(原生显示器) |
| 布局 UI | 需自绘拖拽面板(小工作量) | **无需**(用 Windows 显示设置) |
| 视频管线 | **不需要**(仅输入事件,KB/s 级) | **必须**(捕获+编码+传输+解码,评估中 ≈12 周量级的大头) |
| 当前进度 | S0 已打通双端输入通道(含真机演示),可直接进 S1 | 零;需先装 VDD 验证抓帧链路 |

### 9.4 裁决建议(附 2026-10-16 用户裁决)

> **用户裁决(2026-10-16):两种模式都要** —— ①"一套键鼠直接穿越边缘操作受控机器的原生桌面"与 ②"其他设备屏幕作为主控机的系统扩展屏(模拟第二显示器)"**均为正式需求**。原评估"建议只做边缘穿越、扩展屏无限期推迟"作废,扩展屏路线改为 VDD 方案落地。

**产品结构(两种模式共用一套底座)**:
- 共用:归属者/信任模型、设备发现、配对、输入事件通道(已实测)、设备面板 UI
- 模式 A 边缘穿越:各机保留原生桌面;需捕获端钩子(吞边+隐藏光标+warp)+ 布局拖拽面板 + 远端真注入
- 模式 B 虚拟扩展屏:主控端装 VDD(Windows,已签名,MIT)获得真显示器 → 桌面复制抓帧 → 视频管线串流 → 远端全屏显示 + 输入回注

**视频管线(仅模式 B 需要)**:捕获(DXGI Desktop Duplication)→ 编码(H.264/VP9 硬件优先)→ 传输(TLS 通道)→ 解码显示;无 B 帧/低延迟调参,有线目标 40–80ms。此管线同时反哺"窗口投放(形态 A)"及未来画面查看类需求。

**执行顺序建议**:
1. S1 边缘穿越先行:输入通道已打通,增量 = 边缘切换逻辑 + 布局面板 + 各端捕获注入适配,无需视频管线
2. VDD 实验包(1 天,先于视频立项):验证 `VDD 装屏 → Desktop Duplication 抓帧 → 输入回注` 闭环;通过后再评估视频管线立项
3. 两模式在 UI 上共用一个"设备面板":模式 A 展示为布局拖拽(每设备一块屏),模式 B 展示为"扩展此显示器"

**保留的注意事项**:VDD 官方警告——大版本显卡驱动更新前须先卸载 VDD,否则可能开机黑屏(安装引导必须写入);Miracast 模拟投屏协议路径**否决**(见 9.2);模式 B 的延迟验收标准(40–80ms)与模式 A(毫秒级)分开制定。

## 10. 补充评估(2026-10-17,用户提出):"将其他设备虚拟化为网络/无线投屏设备"的可能性

> 用户设想:让目标设备(Ubuntu/手机等)对外表现为一个**网络显示设备或无线投屏接收设备**,使得主控端(Windows)无需本地虚拟显示驱动,直接"投射"过去。

### 10.1 路径盘点

| 路径 | 原理 | 可行性 | 结论 |
|---|---|---|---|
| A. 目标端实现 Miracast(WFD)接收器 | Ubuntu 等设备实现 Wi-Fi Direct 组网 + WFD RTSP 协商 + H.264 RTP 解码 + UIBC 回传 | ❌ 开源界无可用接收器实现(MiracleCast 已死);依赖特定无线硬件与 Wi-Fi Direct 并发;HDCP/固件问题成堆;典型延迟 100–300ms,不比现方案好 | **否决** |
| B. Miracast over Infrastructure(MICE) | 微软扩展:投屏走普通局域网 TCP,不依赖 Wi-Fi Direct | ❌ 接收端仍需实现微软扩展;仅 Surface Hub 等少数设备支持;更冷门 | **否决** |
| C. 主控端虚拟显示驱动(现状方案) | Windows 端装已签名 VDD 得到本地真显示器;画面经 AnyShare 流到目标端显示 | ✅ **已实测打通**(37ms 级),零自研驱动、零签名成本 | **确立** |
| D. 第三方网络显示产品(时用评估) | spacedesk(AirServer 等)同构:主控端驱动 + 各端 Viewer | 商用闭源,不可作引擎;但验证了"驱动 + 网络 Viewer"是行业通行架构(与 C 一致) | 参考 |

### 10.2 结论

**"把目标设备模拟成投屏设备"在生产约束下不可行**(技术实现、硬件依赖、延迟、开源生态四项全不及格);其想达成的 UX("目标屏成为主控的真实第二屏")**已由主控端 VDD 方案等效实现**——差别只在:显示器"注册"在主控端而不是目标端,这反而是优点(布局 UI、DPI、光标全为系统原生行为,不依赖目标端任何特权)。

后续一切模式 B 工程投入按 [推流优化方案.md](./E2-S0/推流优化方案.md) 执行:GStreamer/FFmpeg 媒体层 + WebRTC 传输层 + 硬件加速探测链(独显→核显→CPU)+ 脏区按需编码。
